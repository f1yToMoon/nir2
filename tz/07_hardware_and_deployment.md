# 07. Ресурсы и развёртывание на одном ПК

## 1. Вывод

Работа **реализуема на одном ПК**. GPU не требуется: модели — градиентный бустинг на десятках тысяч строк. Узкое место — ОЗУ (JVM Spark/Flink) и диск (данные таблицы и снапшоты), а не CPU.

| Конфигурация | CPU | ОЗУ | Диск | Что запускается |
| --- | --- | --- | --- | --- |
| Рекомендуемая (`full`) | 8 ядер / 16 потоков | 32 ГБ | NVMe SSD, 200 ГБ свободно | Всё: Spark (2 воркера), Flink, Kafka, CAPL, наблюдаемость; данные 30 млн строк |
| Минимальная (`lite`) | 6 ядер / 12 потоков | 16 ГБ | SSD, 80 ГБ свободно | Без Flink и Kafka (поток — Spark Structured Streaming), 1 воркер Spark, данные 9 млн строк |
| Симулятор и обучение | любое | 8 ГБ | 10 ГБ | Python, без Docker |

На Windows — Docker Desktop с WSL2; в `.wslconfig` выделить `memory=28GB`, `processors=14` (для full). На macOS (Apple Silicon) образы Spark/Flink работают через arm64-сборки; отдельная проверка на этапе 0.

## 3. Диск

- Данные таблицы: 4–6 ГБ (full), плюс файлы прогонов до уборки: ≈ 1–3 ГБ на прогон. `make gc` после каждого прогона в пакетном режиме.
- Телеметрия Postgres: ≈ 50–200 МБ на прогон (основной объём — `commit_attempts`, `commit_partitions`, `table_health`); экспорт в Parquet ≈ 10–30 МБ на прогон; итого за все серии ≈ 10–20 ГБ.
- Kafka: retention 6 ч.
- Spark event logs: ≈ 50 МБ на прогон; очищать после экспорта стоимости.

## 4. Почему этого достаточно для выводов

1. **Семантика конфликтов не зависит от масштаба**: исход определяется последовательностью коммитов и пересечением следов, а не объёмом данных. Стенд воспроизводит реальный код Iceberg/Spark/Flink и реальный CAS каталога.
2. **Временной масштаб сжат согласованно**: длительность компакции (минуты вместо часов) и периоды потоковых коммитов (секунды) уменьшены пропорционально, так что ключевой безразмерный параметр — ожидаемое число конфликтующих коммитов за время операции $\lambda D$ — лежит в том же диапазоне (0.1–10), что и в промышленных системах.
3. **Промышленный масштаб** (тысячи партиций, сотни ГБ компакции, сутки модельного времени) оценивается на симуляторе, проверенном на стенде (AC-6).
4. **Задержка объектного хранилища** эмулируется Toxiproxy (серия E6).

Распределённость обеспечивается архитектурно: Spark standalone с несколькими воркерами, Flink JobManager/TaskManager, Kafka, отдельные каталог и объектное хранилище — все компоненты взаимодействуют по сети так же, как в кластере. При наличии доступа к кластеру (кафедральный или облачный) тот же `docker-compose.yml` переносится на Kubernetes без изменения кода CAPL и runner (опционально, вне обязательной части).

## 5. Развёртывание

```bash
git clone https://github.com/f1yToMoon/nir.git && cd nir
cp infra/.env.example infra/.env        # проверить VERIFY-теги, при необходимости ресурсы
make build                              # образы capl, spark, flink
make up                                 # full: ядро + streaming + observability
make smoke                              # проверки этапа 0
make seed SCENARIO=S2_compaction_vs_cdc_merge
make run SCENARIO=S2_compaction_vs_cdc_merge POLICY=P0 CONC=mid SEED=11
open http://localhost:3000              # Grafana (дашборд CAPL)
```

Профиль lite: `make up-lite`. Lakekeeper: `make up-lakekeeper` (выставляет `CAPL_UPSTREAM_URI`).

Порты на хосте: 3000 Grafana, 4040 Spark UI драйвера, 5432 Postgres, 8080 Spark master, 8081/8082 воркеры, 8083 Flink SQL Gateway, 8085 Flink UI, 8180 прокси, 8181 каталог, 8182 Lakekeeper, 8190 advisor, 8333 S3, 8474 Toxiproxy API, 9090 Prometheus, 9092 Kafka, 9101 метрики CAPL, 9333 SeaweedFS UI, 18333 S3 через Toxiproxy.
