# 08. Валидация и тестирование

## 1. Уровни тестирования

| Уровень | Каталог | Запуск | Что проверяет |
| --- | --- | --- | --- |
| Unit | `tests/unit` | `make test-unit` (без Docker) | парсер коммитов, матрица, аналитическая модель, признаки, политики, симулятор |
| Integration | `tests/integration` | `make test-int` (стенд поднят) | прокси с реальным каталогом, обогащение, runner-операции, матрица конфликтов |
| E2E | `tests/e2e` | `make test-e2e` | короткий прогон каждого сценария (5 мин), инварианты, наличие метрик |
| Acceptance | `analysis/acceptance.py` | `make acceptance` | AC-1…AC-8 по данным серий |

CI (GitHub Actions) — только unit, линтеры и типизация; integration и e2e — локально.

## 2. Обязательные unit-тесты

| Модуль | Тест |
| --- | --- |
| `capl.proxy.commit_parser` | Разбор фикстур реальных тел коммитов (append, overwrite, replace, delete, MoR с delete-файлами, Flink с `flink.job-id`, транзакционный коммит); классификация `op_class` |
| `capl.conflicts` | Для каждой строки `conflict_matrix.yaml` функция `conflicts()` возвращает ожидаемое; property-тест (hypothesis): append никогда не получает K2 |
| `capl.models.analytic` | Монте-Карло: пуассоновский поток λ, операция длительности D, $q=1$ → доля конфликтов ≈ $1-e^{-\lambda D}$ (допуск 2σ); монотонность по λ, D, |F|; $P_{K1}$ убывает с ростом `num_retries` |
| `capl.features` | Point-in-time: событие с `committed_at = t` не влияет на признаки в момент `t`; детерминизм |
| `capl.policies` | P0 всегда `run_now`; P2 не включает партиции младше N; ограничения SLA и `max_deferrals`; детерминизм при равных оценках; hold никогда не применяется к append |
| `capl.proxy.hold` | Дедлайн соблюдается; освобождение по событию коммита конкурента; отмена при остановке прогона |
| `sim` | Те же пары, что в матрице, дают те же исходы; сохранение числа строк при компакции |

## 3. Проверка матрицы конфликтов (этап 1)

Для каждой пары: ≥ 20 повторов с пересечением следов и ≥ 5 без пересечения (контроль). Детерминизм достигается удержанием коммита `pending` в прокси до завершения `committed` (тестовый эндпоинт `POST /v1/debug/hold`). Результат — таблица наблюдаемых исходов и тепловая карта; запись в `conflict_matrix.yaml: verified`.

## 4. Проверка корректности изоляции (H3, NFR-4)

Прокси не изменяет запросы, поэтому нарушение изоляции может возникнуть только из-за ошибки реализации (например, порчи тела при проксировании). Проверка выполняется в каждом прогоне:

| Инвариант | Проверка |
| --- | --- |
| `ledger_row_counts` | runner ведёт журнал эффектов успешно закоммиченных операций (добавлено/удалено строк по партициям, из `snapshot.summary` и из собственного учёта); итоговое число строк по партициям совпадает с `SELECT dt, bucket, count(*)` |
| `no_duplicate_event_ids` | `SELECT event_id, count(*) ... HAVING count(*) > 1` пусто (exactly-once потока и корректность MERGE) |
| `committed_ops_in_lineage` | каждый `op_id` с исходом `committed` присутствует ровно в одном снапшоте линии `main` |
| `aborted_ops_absent` | `op_id` с исходом `data_conflict`/`retry_exhausted` отсутствует в линии `main` |
| `version_monotonic` | для строк, обновлённых MERGE/UPDATE, `version` равна числу успешно закоммиченных обновлений этой строки (по журналу runner) |
| `proxy_body_integrity` | выборочно (1%) прокси сравнивает SHA-256 тела входящего и исходящего запроса |

Дополнительно: прогоны с одинаковым зерном при P0 и P6 должны давать одинаковое итоговое содержимое таблицы с точностью до операций, исход которых различается (сверка по журналу эффектов).

## 5. Валидация модели (H1)

См. 03_conflict_model.md §4.4. Дополнительно:

- **Утечка данных:** признаки, вычисленные онлайн (сохранены в `decisions.features`), сравниваются с офлайн-пересчётом; модель обучается только на офлайн-признаках, но проверяется на онлайн.
- **Дрейф:** PR-AUC по скользящему окну операций в S6 (дрейф интенсивности); деградация > 0.1 — повод для перенастройки (обсуждается в ВКР как ограничение).
- **Абляция признаков:** без группы «конкуренты», без аналитики, без истории.

## 6. Валидация симулятора (H4)

1. Калибровка на половине прогонов E2 (зёрна 101, 102), проверка — на другой половине и на E3.
2. Метрики сравнения: доля К2, доля отказов К1, доля непроизводительных CPU, p95 латентности коммита; для каждой — относительная ошибка средней по прогонам и пересечение 95% CI.
3. Критерий AC-6: относительная ошибка ≤ 10% для долей конфликтов по S1–S5 при P0, P4, P6.
4. Проверка ранжирования политик: порядок политик по wasted CPU на стенде и в симуляторе совпадает (Kendall τ ≥ 0.8).

## 7. Нагрузочные проверки CAPL

| Проверка | Метод | Критерий |
| --- | --- | --- |
| Накладные расходы коммита | 5000 append-коммитов bypass vs proxy, одинаковая нагрузка | NFR-1 |
| Пропускная способность прокси | синтетический клиент 200 коммитов/с к каталогу-заглушке | без роста ошибок, p95 overhead ≤ 15 мс |
| Advisor | 50 активных операций, 20 intents/с | NFR-2 |
| Очередь обогащения | S1 high | очередь не растёт неограниченно (лаг p95 ≤ 5 с) |

## 8. Критерии завершённости работы

Работа считается выполненной, если: (1) выполнены AC-1, AC-5, AC-6, AC-7, AC-8; (2) для AC-2 и AC-3 получен статистически обоснованный результат — подтверждение или опровержение гипотезы с анализом причин; (3) все графики и таблицы ВКР воспроизводятся командой `make figures` из сохранённых трасс.
