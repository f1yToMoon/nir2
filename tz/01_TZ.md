# 01. Техническое задание

## 1. Общие сведения

| Параметр | Значение |
| --- | --- |
| Наименование работы | Прогнозирование конфликтов оптимистичного контроля параллелизма и конфликт-осведомлённое планирование операций записи и обслуживания таблиц в Data Lakehouse |
| Реализуемая система | CAPL — Conflict-Aware Planning Layer |
| Объект | Таблицы Apache Iceberg (формат v2 и v3) под REST-каталогом |
| Вид результата | Исследовательский прототип, стенд, набор данных, симулятор, результаты экспериментов, текст ВКР |
| Срок | ноябрь 2026 — май 2027 (25 недель, см. [06_implementation_plan.md](06_implementation_plan.md)) |
| Платформа | Один ПК, Linux (или Windows + WSL2), Docker Compose |

## 2. Глоссарий

| Термин | Определение |
| --- | --- |
| OCC | Optimistic Concurrency Control — операции выполняются без блокировок, конфликт проверяется при коммите |
| CAS | Compare-and-swap указателя на текущий metadata.json в каталоге |
| К1 | Конфликт каталога: ответ 409 на коммит; устраняется повтором; становится отказом при исчерпании повторов (`CommitFailedException`) |
| К2 | Конфликт данных: `ValidationException` на клиенте при повторе коммита; работа операции теряется |
| Операция | Единица работы над таблицей, завершающаяся одним коммитом (append, MERGE, DELETE, rewrite_data_files и т. д.) |
| Управляемая операция | Операция, момент запуска которой определяет платформа (обслуживание, пакетные MERGE/DELETE) |
| Неуправляемая операция | Потоковые писатели и пользовательские запросы; учитываются в прогнозе, но не планируются |
| След операции (footprint) | Множество партиций (и при необходимости файлов), которые операция читает/удаляет/переписывает |
| Intent | Регистрация намерения управляемой операции в advisor до её запуска |
| Долг обслуживания (debt) | Мера деградации таблицы при откладывании обслуживания: доля мелких файлов, число delete-файлов на data-файл |
| Непроизводительные вычисления | CPU-секунды исполнителей и записанные байты операций с исходом К2 или отказом К1 |
| Слот (runner slot) | Экземпляр Spark-каталога в исполнителе с уникальным HTTP-заголовком; используется для привязки коммита к операции |
| Политика | Алгоритм принятия решений о запуске/сужении/порядке коммитов (P0–P6, P★) |

## 3. Бизнес-требования

Под «бизнесом» понимается платформа данных организации, эксплуатирующая lakehouse с конкурентной записью.

| ID | Требование | Обоснование |
| --- | --- | --- |
| BR-1 | Снизить потери вычислительных ресурсов от конфликтов коммитов при одновременной работе загрузки и обслуживания таблиц | Конфликт данных обнаруживается в конце операции; потерянная работа оплачивается полностью |
| BR-2 | Не ухудшать актуальность данных потоковой загрузки и не нарушать SLA пакетных операций | Решение не должно «покупать» снижение конфликтов задержкой бизнес-данных |
| BR-3 | Не допускать накопления долга обслуживания сверх заданного порога | Отказ от компакции ухудшает чтение и стоимость хранения |
| BR-4 | Не требовать изменения формата таблицы, клиентских библиотек и каталога | Платформы используют несколько движков (Spark, Flink, Trino) и разные каталоги |
| BR-5 | Обеспечить наблюдаемость: оценку риска конфликта по таблицам и партициям в реальном времени | Даже без управления прогноз помогает эксплуатации |
| BR-6 | Сохранять гарантии изоляции и корректность данных при любом поведении слоя, включая его отказ | Слой не должен стать источником порчи данных или единой точкой отказа |

## 4. Цель и задачи реализации

Цель: создать и экспериментально оценить слой CAPL, который прогнозирует конфликт операции над таблицей Iceberg до её запуска и использует прогноз для планирования, снижая непроизводительные вычисления при ограничениях BR-2, BR-3.

Задачи:

1. Развернуть стенд lakehouse на одном ПК и эмпирически подтвердить матрицу конфликтов Iceberg.
2. Реализовать прокси REST-каталога с журналированием попыток коммита и восстановлением следа коммитов.
3. Реализовать генератор нагрузки и исполнитель операций со сбором исходов и стоимости.
4. Реализовать аналитическую модель риска, advisor и политики P0–P5.
5. Реализовать дискретно-событийный симулятор и откалибровать его по стенду.
6. Обучить ML-модель риска и длительности, реализовать политику P6 и порядок коммитов.
7. Провести серию экспериментов, проверить гипотезы H1–H4 и корректность изоляции.

## 5. Границы проекта

Входит:

- формат Iceberg v2 (основной) и v3 (deletion vectors, дополнительная серия);
- движки записи: Spark 4.0 (пакетные операции, обслуживание, Structured Streaming), Flink 1.20 (потоковая загрузка);
- каталоги: Iceberg REST fixture (основной) и Lakekeeper (проверка неинвазивности);
- операции: append, INSERT OVERWRITE, DELETE/UPDATE/MERGE в режимах copy-on-write и merge-on-read, `rewrite_data_files`, `rewrite_position_delete_files`, `expire_snapshots`, `remove_orphan_files`;
- одна и несколько таблиц, но транзакции в пределах одной таблицы.

Не входит:

- Delta Lake и Hudi (обсуждаются в тексте ВКР качественно);
- мульти-табличные транзакции (`/v1/transactions/commit` проксируется прозрачно и логируется, но не планируется);
- изменение кода Iceberg, Spark, Flink, каталогов;
- промышленное развёртывание, аутентификация, многопользовательский режим.

## 6. Функциональные требования

### 6.1. Стенд (STAND)

| ID | Требование |
| --- | --- |
| FR-STAND-1 | Стенд поднимается одной командой `make up` (профиль `full`) или `make up-lite` и проходит smoke-тест `make smoke` |
| FR-STAND-2 | Все клиенты Iceberg (Spark, Flink, PyIceberg) обращаются к каталогу через прокси CAPL; прямой доступ к каталогу используется только в режиме `bypass` для контрольных прогонов |
| FR-STAND-3 | Обращения к объектному хранилищу идут через Toxiproxy с настраиваемой задержкой (по умолчанию 0 мс; сценарии с 20–80 мс эмулируют S3) |
| FR-STAND-4 | Каталог переключается между REST fixture и Lakekeeper без изменения кода CAPL и runner (только переменные окружения) |
| FR-STAND-5 | Версии всех компонентов зафиксированы в `infra/.env` и проверяются `make versions-check` |

### 6.2. Прокси каталога (PROXY)

| ID | Требование |
| --- | --- |
| FR-PROXY-1 | Прозрачно проксирует все эндпоинты REST-каталога (включая `/v1/config`, OAuth, загрузку таблиц, `/metrics`-отчёты клиентов) с сохранением методов, заголовков, тела и кодов ответа |
| FR-PROXY-2 | Распознаёт запросы коммита: `POST /v1/{prefix}/namespaces/{ns}/tables/{table}` и `POST /v1/{prefix}/transactions/commit` |
| FR-PROXY-3 | Для каждой попытки коммита записывает в телеметрию: время получения, отправки, ответа; задержку удержания; HTTP-статус; таблицу; `assert-ref-snapshot-id`; тип операции и summary из `add-snapshot`; заголовки `X-CAPL-Slot`, `X-CAPL-Writer` |
| FR-PROXY-4 | Привязывает попытку коммита к операции: по заголовку слота и текущему назначению слот → op_id в advisor; резервно — по свойству снапшота `capl.op-id` |
| FR-PROXY-5 | После успешного коммита асинхронно восстанавливает след коммита: читает manifest list и манифесты нового снапшота, извлекает добавленные/удалённые data- и delete-файлы по партициям и публикует событие `commit_event` |
| FR-PROXY-6 | Поддерживает режим удержания коммита (hold) по решению политики: задерживает форвардинг запроса не дольше `hold.max_ms`, затем пропускает без изменений |
| FR-PROXY-7 | Никогда не изменяет тело запроса и не формирует ответ вместо каталога (кроме 502/504 при недоступности каталога) |
| FR-PROXY-8 | При недоступности advisor или внутренней ошибке работает в режиме fail-open: прозрачное проксирование без удержаний |
| FR-PROXY-9 | Экспортирует метрики Prometheus: число коммитов по статусам, латентность, удержания, очередь обогащения |

### 6.3. Advisor (ADV)

| ID | Требование |
| --- | --- |
| FR-ADV-1 | Принимает intent управляемой операции: таблица, тип, режим (CoW/MoR), уровень изоляции, след (список партиций или предикат), оценка объёма, приоритет, допустимая задержка (SLA) |
| FR-ADV-2 | Возвращает решение: `run_now`, `delay(Δ)` с моментом повторного запроса, `narrow(F')` с суженным следом или `reject_scope` (если все партиции рискованны и SLA позволяет ждать); вместе с решением — оценки риска, стоимость и идентификатор решения |
| FR-ADV-3 | Принимает события жизненного цикла операции: `start` (с номером слота), `heartbeat` (прогресс), `finish` (исход, стоимость) |
| FR-ADV-4 | Поддерживает переключаемые политики P0–P6 и режим `explore` (случайные задержки для сбора контрфактических данных); активная политика задаётся при старте прогона |
| FR-ADV-5 | Отдаёт текущую карту риска: для таблицы и партиции — интенсивности по классам писателей, вероятность К2 для типовой операции заданной длительности |
| FR-ADV-6 | Принимает решения о порядке коммитов для прокси (см. 03_conflict_model.md §6) |
| FR-ADV-7 | Пишет каждое решение с признаками и кандидатами в таблицу `decisions` |

### 6.4. Исполнитель нагрузки (RUN)

| ID | Требование |
| --- | --- |
| FR-RUN-1 | Читает сценарий YAML, создаёт таблицы, заливает исходные данные детерминированно по зерну |
| FR-RUN-2 | Запускает неуправляемых писателей (Flink SQL job или Spark Structured Streaming) с параметрами сценария |
| FR-RUN-3 | Генерирует поток управляемых операций по процессу прибытия сценария; для каждой регистрирует intent, выполняет решение advisor, запускает операцию в отдельном потоке с назначенным слотом |
| FR-RUN-4 | Фиксирует исход каждой операции: `committed`, `data_conflict` (`ValidationException`), `retry_exhausted` (`CommitFailedException`), `commit_unknown`, `error`, `skipped`; число попыток, время, стоимость |
| FR-RUN-5 | Стоимость операции определяется по Spark REST API: сумма `executorRunTime` и `executorCpuTime` стадий задач с job group = op_id; байты — из summary снапшота или метрик записи |
| FR-RUN-6 | Каждые 30 с снимает показатели здоровья таблиц (файлы по партициям, мелкие файлы, delete-файлы) в `table_health` |
| FR-RUN-7 | По окончании прогона выполняет проверку инвариантов корректности и подсчёт orphan-файлов |
| FR-RUN-8 | Прогон полностью воспроизводим по `(scenario, policy, seed, versions)`; параметры и git SHA сохраняются в `runs` |

### 6.5. Модели (MODEL)

| ID | Требование |
| --- | --- |
| FR-MODEL-1 | Аналитическая модель рассчитывает $P_{K2}$ и $P_{K1}$ по формулам 03_conflict_model.md §3 на основе матрицы конфликтов и интенсивностей из потока коммитов |
| FR-MODEL-2 | Признаки вычисляются одним модулем `capl.features` и онлайн (advisor), и офлайн (обучение) с point-in-time корректностью: при обучении используются только события до момента intent |
| FR-MODEL-3 | Модель исхода: LightGBM (бинарная К2 и бинарная «отказ К1») с изотонической калибровкой; модель длительности: LightGBM-регрессия логарифма длительности |
| FR-MODEL-4 | Обучение, валидация и регистрация моделей выполняются скриптами с фиксацией версии данных и гиперпараметров; модель загружается advisor по пути из конфигурации |
| FR-MODEL-5 | При отсутствии модели advisor использует аналитическую оценку |

### 6.6. Симулятор (SIM)

| ID | Требование |
| --- | --- |
| FR-SIM-1 | Дискретно-событийная модель (SimPy) таблицы на уровне партиций и файлов с семантикой валидаций из `conflict_matrix.yaml` |
| FR-SIM-2 | Моделирует каталог как сервер CAS со временем обслуживания и клиентские повторы с экспоненциальным backoff по `commit.retry.*` |
| FR-SIM-3 | Использует тот же код политик и признаков, что и advisor (импорт пакета `capl.policies`, `capl.features`) |
| FR-SIM-4 | Калибруется по трассам стенда: распределения длительностей операций по объёму, времени попытки коммита, интенсивности писателей |
| FR-SIM-5 | Пишет результаты в те же таблицы телеметрии (в отдельную схему `sim`), чтобы анализ был общим |

### 6.7. Анализ (ANL)

| ID | Требование |

| FR-ANL-1 | Скрипты расчёта метрик и доверительных интервалов (bootstrap, 10 000 повторов) и статистических тестов |
| FR-ANL-2 | Генерация всех графиков ВКР одной командой `make figures` в `results/figures/` (PNG + PDF) |

## 7. Нефункциональные требования

| ID | Требование | Метрика проверки |
| --- | --- | --- |
| NFR-1 | Накладные расходы прокси на коммит без удержания | p50 ≤ 5 мс, p95 ≤ 15 мс сверх прямого доступа |
| NFR-2 | Ответ advisor на intent | p95 ≤ 100 мс при 50 активных операциях |
| NFR-3 | Fail-open | При остановке advisor прогон продолжается, все коммиты проходят |
| NFR-4 | Корректность | 0 нарушений инвариантов во всех прогонах (08_validation_and_testing.md §4) |
| NFR-5 | Воспроизводимость | Повтор прогона с тем же зерном даёт тот же набор операций; разброс метрик описывается CI |
| NFR-6 | Ресурсы | Профиль `full` укладывается в 28 ГБ ОЗУ, `lite` — в 14 ГБ |
| NFR-7 | Качество кода | Python 3.11, типизация (mypy --strict для `capl`), ruff, покрытие unit-тестами ядра модели и политик ≥ 80% |
| NFR-8 | Наблюдаемость | Все сервисы отдают `/healthz` и метрики Prometheus; логи в JSON |
| NFR-9 | Документированность | Каждый этап завершается обновлением `docs/` и записью в `docs/CHANGELOG.md` |

## 8. Гипотезы и критерии приёмки

| ID | Критерий | Связь |
| --- | --- | --- |
| AC-1 | Матрица конфликтов подтверждена: для каждой пары из `conflict_matrix.yaml` проведено ≥ 20 контролируемых повторов, наблюдаемый исход совпадает с ожидаемым в ≥ 95% (расхождения задокументированы и матрица исправлена) | Задача 1 |
| AC-2 | H1: на отложенных прогонах ML-модель К2 имеет PR-AUC ≥ 0.80, Brier ниже аналитической модели и эвристики P4 (проверка значимости bootstrap) | H1 |
| AC-3 | H2: P6 снижает непроизводительные CPU-секунды ≥ 30% относительно P0 в сценариях S2–S6 при средней и высокой конкурентности, при этом долг обслуживания не превышает P0 более чем на 10% и задержка управляемых операций в пределах SLA для ≥ 95% операций | H2 |
| AC-4 | H2 (сравнение с эвристиками): P6 не хуже P2–P4 по непроизводительным вычислениям при равном долге обслуживания (Манна–Уитни, α = 0.05) | H2 |
| AC-5 | H3: 0 нарушений инвариантов; накладные расходы NFR-1 выполнены; при низкой конкурентности (S0) латентность коммита p50 ≤ +5%, p95 ≤ +10% относительно режима `bypass` | H3 |
| AC-6 | H4: симулятор воспроизводит долю К2 и отказов К1 по сценариям S1–S5 с относительной ошибкой ≤ 10% | H4 |
| AC-7 | Неинвазивность: основная серия P0/P6 повторена на Lakekeeper без изменений кода; качественные выводы совпадают | BR-4 |
| AC-8 | Артефакты: репозиторий, набор трасс (Parquet), обученные модели, графики, инструкции воспроизведения | Открытость |

Промежуточные контрольные точки G1 (после этапа 1) и G2 (после этапа 4, go/no-go) с порогами описаны в [06_implementation_plan.md](06_implementation_plan.md); на них работа останавливается до решения автора.

Если AC-2 или AC-3 не выполняются, результатом считается обоснованное отрицательное заключение с анализом причин (например, низкая предсказуемость при определённых классах нагрузки) — это допустимый научный результат, но его необходимо подтвердить теми же статистическими процедурами.

## 9. Состав результатов

1. Репозиторий `nir` со структурой из [02_architecture.md](02_architecture.md) §5.
2. Стенд (`infra/`), конфигурации (`config/`), спецификации (`api/`, `schemas/`).
3. Пакет `capl` (прокси, advisor, модели, политики, признаки), `runner`, `sim`, `analysis`.
4. Набор данных: `data/traces/*.parquet` — операции, попытки коммита, события коммитов, здоровье таблиц, решения.
5. Модели: `models/<version>/` с метаданными обучения.
6. Результаты: `results/<experiment_id>/` и `results/figures/`.
7. Текст ВКР и презентация.

## 10. Требования к документации

- `docs/CHANGELOG.md` — журнал изменений по этапам.
- `docs/decisions/ADR-XXX-*.md` — архитектурные решения (формат: контекст, решение, последствия).
- `docs/stage-N-report.md` — отчёт по каждому этапу по шаблону `docs/templates/stage_report.md`: что сделано, результаты проверок с числами, отклонения от ТЗ.
- `docs/gate-G1-report.md`, `docs/gate-G2-report.md` — отчёты контрольных точек по шаблону `docs/templates/gate_report.md`.
- Стиль текстов ВКР — по образцу бакалаврской работы: «В данной работе...», формальные определения, таблицы сравнения, обоснование выбора каждого метода с перечислением «Во-первых... Во-вторых...».
