# 06. План реализации

Срок: 25 недель, со 2 ноября 2026 по 25 апреля 2027, затем 4–5 недель на текст ВКР и предзащиту. Каждый этап завершается отчётом `docs/stage-N-report.md`, записью в `docs/CHANGELOG.md` и коммитом с тегом `stage-N`.

Обозначения проверок: **[auto]** — автоматическая проверка командой; **[manual]** — ручная проверка по критерию.

Порядок работы: сначала подтверждается, что проблема реальна и измерима (этапы 0–4), затем строится решение (этапы 5–7), затем проверяются гипотезы H1–H4 о решении (этапы 7–8). Между этими частями стоят **контрольные точки G1 и G2** (см. ниже): на них агент останавливается, пишет отчёт и ждёт явного решения автора работы «продолжаем / корректируем». Без такого решения следующий этап не начинается.

## Этап 1. Эмпирическая матрица конфликтов (2 недели)

**Цель:** подтвердить или исправить `config/conflict_matrix.yaml` для Iceberg 1.12 (v2 и v3) — первый научный результат.

Шаги:

1.1. Реализовать `tests/integration/test_conflict_matrix.py` — параметризованный тест по парам `(pending, committed, isolation, format_version, overlap)`.
1.2. Детерминированная постановка пары (без гонок): операция `pending` запускается и останавливается **перед коммитом**. Способ: выполнить её через Java API Iceberg в py4j (`table.newRewrite()`, `table.newRowDelta()`, `table.newOverwrite()` с `validateFromSnapshot(base)` и тем же набором валидаций, что включает Spark для данного уровня изоляции) либо в Spark с паузой — прокси с hold на слоте `pending` до сигнала теста. Рекомендуемый путь — прокси-hold: он проверяет реальный код Spark-операций; Java API — резервный.
1.3. Пока `pending` удерживается, выполнить `committed` (обычной операцией Spark) с пересечением следа по заданному типу (`partition`/`file`/`none`).
1.4. Отпустить `pending`, зафиксировать исход: успех, `ValidationException` (текст), `CommitFailedException`.
1.5. ≥ 20 повторов на пару с разными данными; отдельно — вариант без пересечения (контроль: должен быть К1 или успех).
1.6. Записать результаты в `verified` секцию YAML (скрипт `scripts/update_matrix.py`) и построить тепловую карту (график 9).
1.7. Зафиксировать тексты исключений для классификации исходов в runner (`runner/ops/errors.py`).

Проверки:

- [auto] `make matrix-verify` — тест проходит, YAML обновлён, расхождения перечислены в отчёте.
- [manual] Каждое расхождение с ожиданием объяснено ссылкой на код валидации Iceberg (класс и метод).

## Контрольная точка G2 — go/no-go (после этапа 4)

**Вопрос:** достаточно ли значима проблема и есть ли в данных сигнал для прогноза, чтобы вкладывать недели в модель и политики?

| Критерий | Порог (согласовать с научным руководителем) | Источник |
| --- | --- | --- |
| Значимость: доля непроизводительных CPU при P0 (`wasted_share`) | ≥ 10% хотя бы в 3 из 5 сценариев S1–S5 на уровне `mid` или `high` | `run_summary` прогонов E2/E3 с P0 |
| Предсказуемость: PR-AUC упрощённой аналитической оценки | ≥ 2 × доля положительных примеров (и 95% CI не пересекает эту границу) | шаг 4.6 |
| Пространство для улучшения: P4 даёт выигрыш над P0 | заметный (> 0) хотя бы в 2 сценариях — подтверждает, что рычаг «момент запуска / сужение» работает | прогоны P0/P4 |
| Объём данных для обучения | ≥ 1500 управляемых операций, из них ≥ 150 с К2 | `stand.ops` |

Возможные решения автора:

- **GO** — все критерии выполнены: переходить к этапу 5.
- **CORRECT** — значимость низкая: усилить сценарии (интенсивности, длительность операций, задержка S3) в пределах правдоподобных значений, повторить сбор; пересмотр фиксируется в ADR **до** любых сравнений политик.
- **PIVOT** — сигнал для прогноза отсутствует: акцент работы смещается на эмпирическое исследование конфликтов (матрица, стоимость, симулятор) и эвристическое планирование; ML-часть сокращается. Это допустимый научный результат.

Действия агента: написать `docs/gate-G2-report.md` по шаблону с числами и графиками (доли потерь по сценариям, PR-кривая оценки), **остановиться** и ждать решения автора.

## Документирование результатов

Документирование — обязательная часть каждого этапа, а не финальный шаг работы. Этап не считается завершённым без отчёта.

| Когда | Что | Где |
| --- | --- | --- |
| Конец каждого этапа | Отчёт по шаблону `docs/templates/stage_report.md`: цель, что сделано, результаты всех проверок **с числами**, отклонения от ТЗ, открытые вопросы, ссылки на коммиты и данные | `docs/stage-N-report.md` |
| Контрольные точки G1, G2 | Отчёт по шаблону `docs/templates/gate_report.md` с таблицей критериев, фактическими значениями и рекомендацией агента | `docs/gate-G1-report.md`, `docs/gate-G2-report.md` |
| Любое изменение решения или расхождение ТЗ с реальностью | ADR: контекст, решение, последствия | `docs/decisions/ADR-NNN-*.md` |
| Каждый этап | Краткая запись | `docs/CHANGELOG.md` |
| Каждый прогон | Параметры, версии, git SHA, итоговые метрики | таблицы `runs`, `run_summary`; экспорт `data/traces/` |
| Каждая версия модели | Данные, гиперпараметры, метрики | `models/<version>/report.md`, `metrics.json` |
| Каждая серия экспериментов | Таблицы и графики, статистика | `results/<series>/summary.md` |

Отчёты пишутся в научном стиле (см. `AGENTS.md`), чтобы фрагменты можно было переносить в ВКР.
