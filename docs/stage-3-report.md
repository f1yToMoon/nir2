## 2. Что сделано

- `src/runner/scenario.py` (3.1): pydantic-модели сценария (`extra=forbid`), `extends` с глубоким слиянием, варианты и переопределения матрицы (операции патчатся по `id`, неизвестный `id` — ошибка), уровни `low/mid/high` по семантике tz/05 §2, профиль `lite`. Проверки согласованности: `statement` соответствует классу операции; overwrite с `isolation_level_option` требует `validate_from_snapshot_id: planning_snapshot` (ADR-006); `rewrite_deletes` не планируется в v3; фоновый и управляемый expire не совмещаются. `make validate-config` проверяет все сценарии × варианты × размеры и `matrix.yaml`.
- `src/runner/intents.py` (3.1, NFR-5): план управляемых операций прогона из зерна — времена прихода (fixed с фазой по зерну, poisson, прореживание для дрейфа S6), следы селекторов `recency_zipf`, `keys_all_days`, `single_day`, `table`, зерно каждой операции. Функция bucket Iceberg (murmur3 для long) сверена со спецификацией и с PyIceberg на 20 000 ключей. Селекторы `small_files_topn` и `delete_files_topn` разрешаются в момент запуска по последнему снимку здоровья таблицы.
- `src/runner/datagen.py`, `runner.main seed` (3.2): «золотая» таблица — 30 млн строк выражениями Spark SQL от `(id, seed)`, 40 пакетов (по одному файлу на партицию за пакет), один снапшот с тегом `golden`; свойства сценариев — поверх него (ADR-009). Генераторы событий потоков и строк MERGE по зерну; непересекающиеся диапазоны `event_id` по источникам.
- `src/runner/slots.py` (3.3): каталоги `s0..s7` (управляемые), `m0, m1` (фоновое обслуживание), `a0..` (агенты), `lake` (служебный). Привязка слот → (`op_id`, класс) в прокси перед операцией, job group + job tag = `op_id`, FAIR-пул по `spark_pool_by_type`.
- `src/runner/ops/executor.py` (3.4): SQL всех `statement` (`merge_upsert`/`merge_update` с материализованным пакетом, `update_status`, `delete_by_keys`), overwrite (`INSERT OVERWRITE … WITH ('isolation-level', 'validate-from-snapshot-id' = снапшот планирования)`), `rewrite_data_files`, `rewrite_position_delete_files`, `expire_snapshots`. Исходы — по классификатору этапа 1 с подтверждением `base_expired` данными (S2-R4-05). Снапшот планирования и время последней попытки коммита (из журнала прокси) пишутся для проверки R.
- `src/runner/cost.py` (3.5): CPU и время задач по job tag через REST API драйвера, все попытки стадий, повтор при неполных данных (ADR-009 п. 2).

## 6. Проблемы и открытые вопросы

- **Долг обслуживания.** «Мелкий файл» в `table_health` — < 32 МБ (tz/05 §3). Партиция занимает ≈ 15 МБ (3,66 ГБ / 240), поэтому даже после компакции файл остаётся «мелким», и `debt_mean` всегда равен 1,0 (S1 `dbg`). Для этапа 4 (P2/P3, «равный долг») нужно определение, зависящее от размера партиции. Например, доля партиций с числом файлов ≥ `min_files` или средняя доля файлов на партицию сверх одного. Решение — до прогонов E3.
- **K2 без попытки коммита.** У CoW MERGE/DELETE, MoR UPDATE и overwrite с K2 почти всегда `attempts = 0`: проверка конфликта срабатывает в `SnapshotProducer.apply()` по обновлённой базе до HTTP-запроса: `commit()` → `apply()` (`SnapshotProducer.java:500`) → `refresh()` (`:296`) → `validate(base, parent)` (`:376`), и только затем `taskOps.commit` (`:533`). Если конкурент закоммитился раньше, чем операция дошла до коммита, конфликт обнаруживается без запроса в каталог. Прокси такие отказы не видит. Метки исходов берутся из runner (ограничение 6), так что метрики H2 это не затрагивает, но это важно для удержания (hold) на этапе 5: удержание меняет только порядок запросов, дошедших до прокси.
