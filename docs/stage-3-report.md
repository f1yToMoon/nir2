## 2. Что сделано

- `src/runner/scenario.py` (3.1): pydantic-модели сценария (`extra=forbid`), `extends` с глубоким слиянием, варианты и переопределения матрицы (операции патчатся по `id`, неизвестный `id` — ошибка), уровни `low/mid/high` по семантике tz/05 §2, профиль `lite`. Проверки согласованности: `statement` соответствует классу операции; overwrite с `isolation_level_option` требует `validate_from_snapshot_id: planning_snapshot` (ADR-006); `rewrite_deletes` не планируется в v3; фоновый и управляемый expire не совмещаются. `make validate-config` проверяет все сценарии × варианты × размеры и `matrix.yaml`.
- `src/runner/intents.py` (3.1, NFR-5): план управляемых операций прогона из зерна — времена прихода (fixed с фазой по зерну, poisson, прореживание для дрейфа S6), следы селекторов `recency_zipf`, `keys_all_days`, `single_day`, `table`, зерно каждой операции. Функция bucket Iceberg (murmur3 для long) сверена со спецификацией и с PyIceberg на 20 000 ключей. Селекторы `small_files_topn` и `delete_files_topn` разрешаются в момент запуска по последнему снимку здоровья таблицы.
- `src/runner/datagen.py`, `runner.main seed` (3.2): «золотая» таблица — 30 млн строк выражениями Spark SQL от `(id, seed)`, 40 пакетов (по одному файлу на партицию за пакет), один снапшот с тегом `golden`; свойства сценариев — поверх него (ADR-009). Генераторы событий потоков и строк MERGE по зерну; непересекающиеся диапазоны `event_id` по источникам.
- `src/runner/slots.py` (3.3): каталоги `s0..s7` (управляемые), `m0, m1` (фоновое обслуживание), `a0..` (агенты), `lake` (служебный). Привязка слот → (`op_id`, класс) в прокси перед операцией, job group + job tag = `op_id`, FAIR-пул по `spark_pool_by_type`.
- `src/runner/ops/executor.py` (3.4): SQL всех `statement` (`merge_upsert`/`merge_update` с материализованным пакетом, `update_status`, `delete_by_keys`), overwrite (`INSERT OVERWRITE … WITH ('isolation-level', 'validate-from-snapshot-id' = снапшот планирования)`), `rewrite_data_files`, `rewrite_position_delete_files`, `expire_snapshots`. Исходы — по классификатору этапа 1 с подтверждением `base_expired` данными (S2-R4-05). Снапшот планирования и время последней попытки коммита (из журнала прокси) пишутся для проверки R.
- `src/runner/cost.py` (3.5): CPU и время задач по job tag через REST API драйвера, все попытки стадий, повтор при неполных данных (ADR-009 п. 2).
- `src/runner/streaming.py` (3.6): продюсер Kafka по зерну (темп × `stream_rate_mult` × дрейф), задание Flink через SQL Gateway по шаблону `infra/flink/sql/streaming_append.sql` (топик на прогон, `earliest-offset`), остановка после нулевого лага группы и ещё двух чекпойнтов; Spark-агенты S1.
- `src/runner/health.py`, `src/runner/metadata.py`, `src/runner/invariants.py` (3.7): версия metadata и три времени наблюдения, кэш агрегатов immutable манифестов и два процесса spawn (ADR-014/015); `table_health` раз в 30 с (файлы, мелкие файлы, delete-файлы по партициям) и `table_meta` (число снапшотов, байты `metadata.json`). Пять инвариантов tz/08 §4 по журналу эффектов runner, который не зависит от таблицы. Orphan-файлы считаются как разность множеств по листингу хранилища: процедура `remove_orphan_files` не принимает интервал < 24 ч.
- `src/runner/main.py`, `batch.py`, `export.py`, `gc.py` (3.8): протокол прогона tz/05 §4. Перед прогоном — уборка файлов прошлых прогонов и регистрация «золотых» метаданных; затем потоки, фоновый expire (ADR-008), управляемые операции P0, остановка, финализация (`footprint_executed` из журнала прокси), инварианты, orphan-файлы, `run_summary`. Серии возобновляемые; экспорт трасс — в Parquet.
- `src/analysis/metrics.py` (3.9): `run_summary` по tz/05 §3 плюс `n_base_expired`, `n_history_unresolved`, `wasted_cpu_base_expired_s`, `background_cpu_s` и `detail` (исходы и длительности по операциям, фоновый expire, история таблицы).
- Прокси: в `commit_attempts` пишутся `removed_snapshot_ids` коммитов expire — доказательство для `base_expired`.
- Тесты: 347 unit для сценариев, исходов, матрицы, возобновления, стоимости, времён, metadata и управления процессами; интеграционные контроли эффектов, сессий, инъекций и реальной истории. Проверки этапа — scripts/stage3_checks.py; точные команды и результаты — §31.

## 6. Проблемы и открытые вопросы

- **Долг обслуживания.** При пороге мелкого файла 32 МБ и партиции≈15 МБ даже
  скомпактированный файл остаётся мелким, debt_mean=1,0. До базовых политик
  следующего этапа нужно авторское определение долга, учитывающее размер партиции;
  агент его не меняет. Возможные варианты — число файлов сверх одного или доля
  партиций с числом файлов≥min_files. Решение не следует подбирать после E3.
- **Прямой bypass.** Подтверждён routing=proxy. До E1 нужно реализовать прямые
  provenance, свежесть и инварианты без журнала прокси, затем различающий контроль
  (S3-R1-04). Отказ bypass не является измерением его накладных расходов.
- **Область NFR-1.** Последовательный бенчмарк этапа 2 не становится гарантией
  добавки RTT при параллельной нагрузке S1; такой новый опыт здесь не выполнен.
- **Диагностическая нагрузка и профиль.** Дополнительные чтения и два процесса
  health, пакетные Spark-агенты, реальные размеры золотых файлов ADR-009 оговаривают
  область применимости. CPU задач Spark не равен CPU всей среды.
- **K2 до HTTP.** Клиент может отвергнуть операцию в SnapshotProducer.apply()
  до отправки запроса: commit→apply/refresh/validate предшествует taskOps.commit
  (Iceberg1.12.0 SnapshotProducer.java:296,376,500,533). Метки берутся из runner;
  прокси такие отказы не наблюдает, что существенно для будущего hold.
- **PostCompact.** Историческая несовместимость Caveman со схемами Codex0.167/0.169
  отделена от CAPL SessionStart/PreToolUse в §18. Исходный stderr не восстановлен;
  защитные настройки не менялись, исправление внешнего обработчика не заявлено.
