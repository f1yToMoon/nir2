# ADR-013: Владение SparkSession и кэшем в пределах операции

**Статус:** исправление реализации runner; научные требования не меняются.
**Дата:** 15.11.2026. Связано с ADR-010/011/012.

## Отказ и проверяемый механизм

S4 `stage3-S4-P0-mid-s11-r540-20261108` невалиден: две операции MERGE
завершились `IllegalStateException: Runtime file filtering is not possible`.
Они остаются `error`, а прогон — диагностическим. Он не включается в итоговую
квалификацию, даже при пяти пройденных инвариантах.

В Iceberg 1.12.0 (пути относительно `third_party/iceberg-src/`):

| Источник | Поведение |
| --- | --- |
| `spark/v4.0/spark/src/main/java/org/apache/iceberg/spark/source/SparkScanBuilder.java:699–729` | CoW scan закрепляет текущий снимок |
| `SparkCopyOnWriteScan.java:107–114,181–183` в том же каталоге | runtime filter сравнивает закреплённый снимок с текущим снимком объекта Table |
| `SparkTable.java:338–340` в том же каталоге | при refreshEagerly повторный newScanBuilder обновляет тот же объект Table |
| `spark/v4.0/spark/src/main/java/org/apache/iceberg/spark/SparkCatalog.java:898` | refreshEagerly = !cacheEnabled |

Микрокейс `tests/integration/test_runner_sessions_stage3.py` выполняется на
Spark-кластере с executor 2g. После закрепления CoW scan другой append меняет
снимок; затем выполняется загрузка для следующего запроса и runtime filter
исходного scan. Проверены все четыре сочетания кэша и владения сессией:
без кэша повторный newScanBuilder вызывает тот же IllegalStateException даже
при отдельной сессии писателя; с кэшем общий писатель меняет объект Table;
с кэшем и отдельной сессией scan стабилен, а другая сессия видит обе строки.
Четыре различающих случая прошли до исправления runner, сохранив три ожидаемых
воспроизведения дефекта: `results/stage-3/sessions-causal-writer-20261115/`.

Первый вариант микрокейса ошибочно ожидал, что refreshTable после внешней
фиксации изменит старый кэшированный объект. Это предположение отвергнуто:
1 failed / 3 passed, `sessions-causal-20261115/`. RefreshTable инвалидирует
запись, но не обязательно меняет объект старого scan. Исправлен контроль
самого опыта: append через проверяемую сессию. Первый результат сохранён.

## Исправление и границы владения

Каждая управляемая и фоновая операция получает новую нативную SparkSession.
В её целевом каталоге слота кэш включён до первой загрузки таблицы. Каталоги
и временные представления не разделяются между операциями, а первая загрузка
новой операции свежая. Общий RunCtx не изменяется: дочерний исполнитель получает
dataclasses.replace с новой сессией. Она используется для подготовки MERGE,
SQL, извлечения read snapshot и точных эффектов.

Служебный каталог lake остаётся без кэша. Источники planning VERSION AS OF и
диагностические чтения ADR-011 не получают устаревшую историю. HealthSampler
по-прежнему читает некэшированный lake и сериализует sample своим lock;
Spark-агенты пишут через отдельные a-каталоги, не разделяя Table целевого слота.
Они не могут обновить каталожные объекты приватной сессии операции.

SparkContext, job tags и FAIR-пулы остаются общими; новые приложения и отдельные
ресурсные пулы не создаются. Сессия не останавливается через stop(): это
остановило бы общий SparkContext. Нагрузка не сериализуется. Код Spark/Iceberg,
SQL сценариев, R=540 с и научные пороги не меняются.

## Проверки

К причинному микрокейсу добавлена проверка настоящего OpExecutor.execute:
две операции получают разные сессии, общий SparkContext и разные временные
представления, исходный RunCtx не меняется. Шестнадцать случаев ADR-011 повторяются
с приватной сессией и кэшированным target, включая устаревшее планирование.
Итоговые числа, новые полные run_id и стоимость приведены в отчёте этапа 3.
Микрокейс устанавливает механизм; частота отказов и пригодность исправления
под нагрузкой проверяются новой полной серией, а не выводятся из четырёх случаев.
