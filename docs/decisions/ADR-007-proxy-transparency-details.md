# ADR-007: Прозрачность прокси — уровень HTTP-сообщения, коды 2xx коммита, классификация по телу

**Статус:** Предложено (этап 2; редакция 2 — по ревью stage-2-r1)
**Дата:** 2026-10-31
**Связано с:** FR-PROXY-1, FR-PROXY-7, `tz/04_interfaces.md` §1.1–1.2, `AGENTS.md` (ограничение 1)

## Контекст

ТЗ требует, чтобы прокси передавал запросы и ответы «без изменений, кроме hop-by-hop заголовков». На этапе 2 проверки на моке каталога (`tests/unit/test_proxy_transparency.py`) и на стенде (`tests/integration/test_proxy_stage2.py::test_responses_identical_to_catalog`) выявили, что понимать «без изменений» нужно на уровне HTTP-сообщения (метод, цель запроса, поля заголовков, содержимое), а не байтов соединения, и нашли три расхождения реализации прототипа этапов 0–1 с этим требованием.

## Решение

1. **Что сохраняется побайтно (ответы: ревью S2-R1-01):** ответы на коммиты 2xx и все прочие ответы передаются потоком, буферизуются только ответы ≥ 400 на коммит (нужен `error_type`); заголовки ответа — ровно полученные, кроме hop-by-hop (`Content-Length` не дописывается, в том числе к 204/304; chunked остаётся chunked). Далее — тело запроса и тело ответа (ответ — сырые байты, без декодирования `Content-Encoding`), путь и query в исходной кодировке (`%1F`, `%2F`, отсутствие `?` при пустом query), список полей заголовков с повторами и значениями (кроме hop-by-hop: `Connection` и перечисленные в нём, `Keep-Alive`, `Proxy-*`, `TE`, `Trailer(s)`, `Transfer-Encoding`, `Upgrade`), включая `Host` (пересылается как получен). Прокси не добавляет заголовков: у `httpx` убраны заголовки по умолчанию (`User-Agent`, `Accept-Encoding` и др.), у `uvicorn` — `server` и `date`.
2. **Что не сохраняется (ограничение ASGI/h11, не влияет на семантику):** reason-phrase строки статуса (каталог Jetty: `500 Server Error`, прокси: `500 Internal Server Error`) и регистр имён заголовков. Reason-phrase клиенты обязаны игнорировать (RFC 9112 §4), имена полей нечувствительны к регистру (RFC 9110 §5.1). Клиенты Iceberg (Java `HTTPClient`, PyIceberg) используют только код статуса и тело.
3. **Исправления прототипа этапов 0–1:** (а) ответ передавался декодированным (`httpx.Response.content`) с удалённым `Content-Encoding` — теперь сырые байты и исходный заголовок; (б) `httpx` добавлял к запросу каталога свои заголовки по умолчанию — убраны; (в) при пустом query к пути добавлялся `?`, а `%1F` в пути вызывал ошибку — цель запроса берётся из `raw_path`/`query_string`.
4. **Успех коммита — любой 2xx.** Каталог отвечает на `POST /v1/transactions/commit` кодом 204 (обнаружено при снятии фикстуры), на коммит таблицы — 200. Постановка в очередь обогащения и освобождение удержания по коммиту конкурента выполняются при 2xx.
5. **Класс операции по телу коммита не всегда определяет валидацию (ревью S2-R1-03).** Операция снапшота (`summary.operation`) зависит только от того, какие файлы добавлены и удалены (`BaseOverwriteFiles.java:50-58`, `BaseRowDelta.java:50-60`), а валидация — от класса коммита и опций записи. Неоднозначные случаи (`capl.proxy.commit_parser.AMBIGUOUS`, у каждого — множество классов-кандидатов из `conflict_matrix.yaml: op_classes`):
   - `data_files_added_only` — `operation=append` без `flink.job-id`: кроме `AppendFiles` так выглядит MERGE только со вставками в CoW (`OverwriteFiles`, `BaseOverwriteFiles.java:54-56`, валидация при serializable `SparkWrite.java:460-476`) и в MoR (`RowDelta.addRows`, `BaseRowDelta.java:51-53`, `SparkPositionDeltaWrite.java:282-284`). Кандидаты: `append`, `cow_dml`, `mor_dml`. Подтверждено реальными телами (`spark_cow_dml_merge_insert_only`, `spark_mor_dml_merge_insert_only`);
   - `overwrite_options` — `replace-partitions=true`: проверка конфликтов включается только опцией записи `isolation-level` (`SparkWrite.java:353-356`), которой нет в теле. Кандидаты: `overwrite` (K1), `overwrite_opts` (K2);
   - `overwrite_by_filter` — `operation=overwrite` без delete-файлов и без `replace-partitions`: CoW DML и статический `INSERT OVERWRITE … PARTITION` (`OverwriteByFilter`, `SparkWrite.java:374-404`). Кандидаты: `cow_dml`, `insert_overwrite`, `insert_overwrite_opts`;
   - `data_files_removed_only` — `operation=delete` без delete-файлов: metadata delete (`StreamingDelete`, без валидации, `StreamingDelete.java:73-78`, `SparkTable.java:458-462`) или CoW `OverwriteFiles`, удаливший файлы целиком (с валидацией). Кандидаты: `cow_dml`, `metadata_delete` (новый класс в `op_classes`, пары с ним на этапе 1 не проверялись).

   **Истинный класс операции берётся из привязки слот → (`op_id`, тип операции)** (FR-PROXY-4; на этапе 2 — `PUT /v1/debug/slots/{slot}`, с этапа 3 — `POST /v1/intents/{id}/start`). В журнал пишутся: `commit_attempts.op_class` (по привязке, иначе по телу), `op_class_body`, `op_class_ambiguity`, `op_class_source` (`op_id` | `body`); `commit_events.op_class` и `op_class_source`. Модель и политики (этапы 5+) используют класс только при `op_class_source = op_id` или `op_class_ambiguity IS NULL`; для неуправляемых писателей (поток Flink) класс по телу точен (`flink.job-id`).
6. **Режимы:** `proxy.mode = full | passthrough` (`passthrough` — только пересылка, без разбора, журнала и удержаний; переключается `PUT /v1/debug/mode`); контрольные прогоны `bypass` по-прежнему задаются маршрутизацией клиентов (`CATALOG_ROUTING=bypass`, клиенты → каталог напрямую), прокси в них не участвует.

## Последствия

- Проверка «тело и заголовки не изменены» выполняется сравнением SHA-256 тела и мультимножества заголовков на входе прокси и на входе транспорта `httpx` (`IntegrityTransport`, доля выборки `proxy.integrity_sample_rate`, по умолчанию 1 %), результат — метрика `capl_body_integrity_total{result}`.
- Сравнение ответов прокси и каталога в тестах ведётся при одинаковом `Host`: каталог вписывает полученный `Host` в HTML-страницы ошибок.
- Ответ на коммит содержит полные метаданные таблицы (сотни КБ — единицы МБ при тысячах снапшотов). Обогащение ставится в очередь после того, как клиенту передан последний байт ответа (а также при обрыве соединения клиентом), и декодирует манифесты в пуле процессов (`enricher.executor = process`). Иначе чтение manifest list идёт одновременно с передачей ответа и увеличивает задержку коммита с ростом таблицы (ревью S2-R1-02).
