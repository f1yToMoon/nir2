# ADR-011: Снимок фактического чтения для журнала эффектов

**Статус:** принято — исправление реализации независимой проверки NFR-4.
**Дата:** 08.11.2026. Уточняет ADR-010, пункт 2; научные пороги и SQL сценариев не меняет.

## Проблема и различающий опыт

Родитель успешной фиксации не всегда совпадает со снимком, который прочитала операция. При изоляции снимка (`snapshot isolation`) параллельный append после чтения DELETE/UPDATE может быть зафиксирован раньше DML. Родитель DML содержит новые строки, но DML их не читала. Повторное применение её предиката ко всему родителю ошибочно приписывает ей изменение этих строк.

`tests/integration/test_runner_effects_stage3.py` принудительно задаёт порядок чтение DML → фиксация append → фиксация DML через штатный hold до 60 с. Начальные строки: `event_id=1,key=97` и контрольная `event_id=2,key=98`; поздняя строка — `event_id=3,key=97`. При snapshot поздняя строка осталась с version=0 после UPDATE и сохранилась после DELETE, а прежний журнал включил её в эффекты. Результат до исправления: **4 failed / 4 passed** (CoW/MoR × UPDATE/DELETE, snapshot и serializable); serializable — отвергающий контроль. Сырые наблюдения и полный журнал сохранены в `results/stage-3/effects-snapshot-before/`.

Это опыт с принудительным порядком, а не оценка частоты конфликта под нагрузкой.

## Источник фактического снимка

Исходники клиента Iceberg 1.12.0, пути относительно `third_party/iceberg-src/`:

| Путь | Поведение |
| --- | --- |
| `spark/v4.0/spark/src/main/java/org/apache/iceberg/spark/source/SparkScanBuilder.java:655,668–680` | MoR закрепляет текущий снимок в параметрах и объекте сканирования |
| тот же файл `:699,713–729` | CoW закрепляет снимок аналогично |
| `SparkCopyOnWriteScan.java:85`, `SparkBatchQueryScan.java:95` в том же каталоге | `snapshotId()` возвращает закреплённый ID |
| `SparkWrite.java:497–499,520–522`, `SparkPositionDeltaWrite.java:271–274` | Этот ID используется в `validateFromSnapshot` |

Успешная команда Spark сохраняет физический план под `CommandResult`, адаптивным планом и стадиями запроса. `runner.read_snapshot.read_snapshot_id` обходит его, выбирает Iceberg scan именно каталога слота и читает `snapshotId()` и имя таблицы через Java reflection: методы package-private/protected. Клиенты и их код не меняются; новое Spark-задание не запускается. Не найденный либо неоднозначный ID — ошибка журнала, без подстановки снимка планирования или конечной таблицы.

## Решение

1. Сохранить DataFrame фактически исполненной SQL-команды; после подтверждения фиксации получить ID её target scan. Записать `read_snapshot_id` в журнал операции.
2. Предикаты DELETE/UPDATE и сопоставление источника MERGE применять к `VERSION AS OF read_snapshot_id`. Независимое ожидание по-прежнему строится из входных строк и правила операции, а не из разности конечных таблиц.
3. Родителя успешного снимка сохранять отдельно как `effects_parent_snapshot_id`; `effects_read_snapshot_id` явно указывает использованный вход. Порядок проигрывания эффектов остаётся порядком линии успешных фиксаций.
4. Снимок планирования остаётся отдельным полем: он может отставать от фактического чтения, пока runner готовит SQL. У overwrite его прежняя роль `validate-from-snapshot-id` не меняется.

## Проверка и ограничения

После исправления проверено **16/16 случаев**: оба режима записи, оба statement, оба уровня изоляции, с устаревшим и актуальным снимком планирования. При отставании дополнительная подходящая строка `event_id=4` вставлена до фактического чтения: она должна войти в эффекты, тогда как поздняя `event_id=3` — нет. ID плана совпал с ожидаемым read snapshot; выбор каталога, отличного от слота, отвергается. Результаты — `effects-snapshot-after/`; JSON без суффикса lag — более ранние восемь успешных технических случаев, итоговая расширенная серия — файлы `*_lag{0,1}.json`.

Доступ к физическому плану и reflection привязаны к проверенным Spark 4.0.1 / Iceberg 1.12.0. При смене версий эту интеграционную проверку нужно повторять; отсутствие совместимого плана не маскируется. Как и в ADR-010, диагностические time-travel чтения журнала создают нагрузку admin-пула и учитываются отдельно от стоимости изучаемой операции.
