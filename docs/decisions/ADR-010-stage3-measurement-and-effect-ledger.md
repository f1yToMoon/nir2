# ADR-010: Полнота стоимости и точный журнал эффектов этапа 3

**Статус:** Принято (исправление реализации требований FR-RUN-5, NFR-4).
**Дата:** 2026-11-07.

## Контекст

Предварительный независимый аудит кода `c4e2579` выявил пропуск CPU подготовки MERGE: `_sql` вызывался до `job_scope`, хотя `_merge` выполняет Spark collect с чтением и сортировкой. Проверка верхней границы CPU не обнаруживает занижения. Сохранённые S0–S3 оставлены как исторические измерения прежней реализации; переносить их стоимости в итоговую оценку исправленного runner нельзя.

Инвариант строк исключал все удалённые ключи одновременно из ожидания и факта. Это скрывало неисполненное удаление и потери поздних событий тех же ключей. Также проверка версий не охватывала часть потоковых строк.

## Решение

1. Область тега и FAIR-пула включает подготовку пакета MERGE и выполнение SQL. Для каждой операции сохраняются исходные счётчики попыток стадий Spark REST API; неполнота стоимости проверяется отдельно, пустой список заданий не считается полным измерением выполненной операции.
2. После успешной фиксации журнал эффектов записывает конкретные удалённые, обновлённые и вставленные `event_id`. Входное состояние — родитель успешного снимка, полученный через метаданные REST и time travel, а не результат над текущей таблицей. Для MERGE сопоставляются материализованный источник и входное состояние. Эффекты проигрываются по цепочке родителей фиксаций.
3. Фактические строки никогда не фильтруются. Из независимого ожидания исключаются только конкретные удалённые события; повторная вставка сбрасывает их ожидаемую версию. Сверка версий выполняется для всех источников строк. Добавлена инъекция сохранившейся удалённой строки.
4. Диагностические чтения для журнала эффектов выполняются отдельно в пуле admin с тегом `effects-<op_id>`. Их CPU входит в CPU приложения, но не в CPU исследуемой операции. Они создают дополнительную нагрузку среды; это ограничение необходимо учитывать при переносе частот конфликтов. Порогов научных проверок решение не меняет.
5. Свежесть потока измеряется отдельно: реальное UTC-время генерации события → успешный ответ каталога исходному append. Логический `event_ts` не используется как физические часы. Наблюдатель сопоставляет event_id с ADDED data-файлами исходного снимка через манифесты и Parquet. При неполном покрытии p95 не публикуется, проверка прогона падает. Ответ каталога задаёт верхнюю границу момента видимости фиксации. CPU диагностического потока наблюдателя приводится отдельно; он не является полным CPU процесса.

## Последствия

Нужны новые полные прогоны с отдельными run_id: старые измерения и журналы не перезаписываются. Сначала проверяется короткий технический опыт, затем S4, S5 и повторная серия для итогового учёта. Параметры исходных сценариев и пороги сохраняются. Локальные pickle-журналы прежней версии несовместимы с точными эффектами; для инъекции используется новый финальный S5.
