# ADR-008: Периодический expire_snapshots в сценариях S1–S6

**Статус:** Принято (решение автора по NFR-1 на этапе 2: варианты (б) + (а), 2026-11-01). Срок хранения R — **предварительный**: он выведен из априорной модели длительностей и перепроверяется на этапе 3 по измеренным длительностям (`tz/06_implementation_plan.md`, этап 3, [auto]).
**Дата:** 2026-11-01; пересмотр 2026-11-04 (ревью S2-R3-02, S2-R3-03, S2-R3-05)
**Связано с:** NFR-1, `docs/stage-2-report.md` §4.2, §6; `config/workloads/_base.yaml: maintenance`; ADR-006 (expire в матрице); `AGENTS.md`, ограничение 6 (`base_expired`); `src/runner/ops/errors.py`

## Уточнение этапа 3 (07.11.2026)

Ниже сохранена исходная априорная оценка. Формула с одним hold и граница 349 с относятся к прежнему расчёту и **не являются текущим правилом выбора R** (S2-R4-04). Для измеренной на P0 длительности D_hist от времени базового снимка до последней попытки/отказа применяется:

R_low = 2·D_hist,max + (num_retries + 1)·hold_max = 2·D_hist,max + 300 с.

Измерение P0 не включает удержания; 300 с — запас на будущие пять запросов по 60 с. При текущем R = 600 с необходимо D_hist,max ≤ 150 с. Для исходного B = 1800 и номинальной интенсивности 2,2/с общий интервал возможен до D_hist,max ≤ 229 с; B имеет неопределённость около ±300 снимков. Непосредственно проверенная рабочая точка — 1452 снимка / 1 509 024 Б (`r9`), поэтому в приёмке этапа 3 используется предел 1452 / 1 510 000 Б. Изменения R требуют пересчёта с фактическими длительностями и интенсивностями; при отсутствии общего интервала решение принимает автор.

Фраза ниже «цена — один коммит expire в минуту» описывает только частоту запросов. Полная стоимость включает Spark-чтение манифестов всех сохранённых снимков и удаление файлов (`ExpireSnapshotsSparkAction.java:173–184,236–246`). Исторический S1 (`3d9f074`): 28 запусков, около 345 CPU-с, длительность около 10 с; у 13 компакций около 290 CPU-с. Эти числа относятся к прежнему runner, не к новой приёмочной серии. В отчёте этапа 3 приводятся отдельные измерения фонового обслуживания, наложений и конкуренции за общий пул maintenance.

## Контекст

На этапе 2 накладные расходы прокси на запрос коммита растут с историей таблицы; размер метаданных (и ответа на коммит) линеен по числу снапшотов, механизм роста добавки не установлен (`docs/stage-2-report.md` §4.3). Время самого каталога растёт тоже: bypass p50 — от 13 до 182 мс за 3000 коммитов (`results/stage-2/r8-boundary/overhead.json`).

Граница NFR-1 измерена на снапшотах размера Spark/Flink (ревью S2-R3-02): записи снапшотов бенчмарка дополнены до 970 Б (цель 960 Б — размер записи `spark_mor_merge_v2`, наибольшей из фикстур Spark; у `spark_append_v2` — 871 Б), метаданные растут на 1037 Б на снапшот (у PyIceberg без дополнения — ~640 Б). Прогон `r8-boundary` (3000 коммитов на путь, без expire), критерий — верхняя граница бутстрепного 95 % ДИ парной медианы по объединённой верхней полосе истории (окна из 100 коммитов с медианой снапшотов в [T − 300, T], 300 пар) ≤ 5 мс:

| T, снапшотов | Метаданные, МБ | Медиана, мс | 95 % ДИ, мс |
| --- | --- | --- | --- |
| 1500 | 1,57 | 3,17 | 2,35…4,19 |
| 1600 | 1,67 | 3,68 | 2,84…4,88 |
| 1800 | 1,88 | 3,83 | 2,90…4,97 |
| 1900 | 1,98 | 4,15 | 2,90…**5,17** |
| 2000–2300 | 2,09–2,40 | 3,0–3,7 | верх 3,63…4,98 |
| 2400 | 2,50 | 4,48 | 3,31…**5,52** |
| 3000 | 3,12 | 6,70 | 4,32…8,81 |

Первое превышение — при 1900 снапшотах; начиная с 2400 превышение устойчивое. Граница принимается консервативно: **B = 1800 снапшотов размера Spark ≈ 1,88 МБ метаданных** (13,8 КБ + 1037 Б × снапшоты).

Сценарии без обслуживания копят историю за весь прогон. В S1 частота коммитов 2,2/с (Flink — раз в 5 с, 6 агентов — раз в 3 с), и к концу измеряемой части набирается ~3700 снапшотов. Свойство `history.expire.max-snapshot-age-ms` (1 сутки) само снапшоты не удаляет: его применяет только `expire_snapshots`.

## Решение

В сценарии добавляется периодический `maintenance.expire_snapshots`. Это **модельное допущение** экспериментальной нагрузки (решение автора, `docs/author-decisions.md`), а не утверждение о практике эксплуатации. Операция выполняется по расписанию, без advisor:

```
CALL system.expire_snapshots(table => 'bench.events', older_than => now() - older_than_s, retain_last => 20)
```

раз в `interval_s`.

### Противоречие при выборе R

Срок хранения R влияет на обе цели в противоположные стороны:

- **короткий R** — меньше история таблицы и меньше задержка коммита (NFR-1). Наибольшая история = rate · (R + I), где I — `interval_s`;
- **длинный R** — меньше потерь работы от expire. Операция не должна лишиться базового снапшота за время работы (решение автора), иначе исход `base_expired` — артефакт обслуживания, а не изучаемый конфликт.

Обозначения:
- D — длительность операции от старта до коммита;
- D_max — наибольшая D по сценариям;
- hold — наибольшее удержание коммита (`hold.max_ms` = 60 с).

Два условия:

1. **Нижняя граница по длительностям:** R ≥ 2·D_max + hold. Множитель 2 — запас на разброс длительности.

   Длительности взяты из априорной модели `config/capl.yaml: analytic.duration_fallback` (D = a + b·ГБ). Следы операций берутся из сценариев, размер партиции — из `seed_data`: 30 млн строк × ~250 Б / 240 партиций ≈ 31 МБ.

   | Сценарий, операция | След | ГБ | D, с |
   | --- | --- | --- | --- |
   | S5 `gdpr_delete` (`cow_dml`, `keys_all_days`, 2 бакета) | 30 дней × 2 бакета = 60 партиций | ~1,9 | 15 + 120·1,9 ≈ 243 |
   | S6 `gdpr_delete` (`cow_dml`, 1 бакет) | 30 партиций | ~0,9 | ≈ 127 |
   | S1 `compaction_hot` (`rewrite_data`, top 16) | 16 партиций | ~0,5 | 20 + 90·0,5 ≈ 65 |
   | S4 `reprocess_day` (`overwrite`, 1 день) | 8 партиций | ~0,25 | 10 + 60·0,25 ≈ 25 |

   D_max ≈ 243 с → **R ≥ 2·243 + 60 = 546 с**.

2. **Верхняя граница по NFR-1:** rate_S1 · (R + I) ≤ B, то есть R ≤ B / rate_S1 − I = 1800 / 2,2 − I = 818 − I.

Интервал I на потери не влияет (см. «Последствия»), но увеличивает историю. При прежнем I = 300 с допустимо R ≤ 518 с < 546 с — общего R нет. При I = 60 с допустимо **R ≤ 758 с**: окно [546; 758] не пусто.

### Параметры

1. **`older_than_s` (R) = 600 с — предварительно.** Это значение из окна [546; 758], округлённое вверх от нижней границы. Запас до верхней границы — 158 с: истории 2,2 · 660 ≈ 1452 снапшота ≈ 1,52 МБ = 0,81·B.
2. **`interval_s` (I) = 60 с.** Цена — один дополнительный коммит expire в минуту: +0,017 коммита/с к 2,2 в S1. Expire коммитит только `remove-snapshots` и данных не трогает (ADR-006).
3. **`retain_last: 20`** — как у управляемой операции `expire` в S6: минимум истории, если коммиты прекратились. Защищает таблицы с редкими коммитами: в S0, S2–S5 за R приходит ~60 коммитов, в S6 — ~75.
4. **S6** сохраняет свою управляемую операцию `expire` (раз в 600 с, `older_than_s: 900`, `retain_last: 20`): она — часть изучаемых явлений (решения advisor, `base_expired`). Фоновая операция в S6 отключена, чтобы два обслуживания не накладывались.
5. Коммит expire проходит через прокси и классифицируется как `expire` (`writer_class: maintenance`). По матрице expire не конфликтует ни как pending, ни как committed (`conflict_matrix.yaml`: `pending: expire` → success; `[rewrite_data, cow_dml, mor_delete, mor_update, mor_merge] × expire` → success). Исключение — `mor_delete × append_expire` → `base_expired`.

**Когда противоречие станет неустранимым.** При I = 60 с общий R существует, пока 2·D_max + 60 ≤ 758, то есть D_max ≤ 349 с. Если на этапе 3 измеренная D_max превысит 349 с или измеренная история S1 превысит B, то R по этому правилу не выбирается. Тогда решение принимает автор. Варианты:
- (а) R по сценариям: в S1 нет операций дольше ~65 с;
- (б) меньший I;
- (в) принять потери `base_expired` в долгих операциях;
- (г) сузить область NFR-1.

## Последствия

### Потери работы по классам операций

Expire удаляет снапшоты старше R при каждом запуске (раз в I).

| Класс | Что удаляется | Исход | Когда теряется работа | Код |
| --- | --- | --- | --- | --- |
| `mor_delete`, `mor_update`, `mor_merge` (RowDelta) | сам базовый снапшот | `IllegalArgumentException` «Snapshot X is not an ancestor of Y» → `base_expired` | возраст базового снапшота к коммиту (t_start − t_base) + D > R; гарантированно при > R + I | `BaseRowDelta.java:134-139`; `SnapshotUtil.isAncestorOf` |
| RowDelta, `cow_dml` (`OverwriteFiles`), `overwrite_opts` / `insert_overwrite_opts` (с `validate-from-snapshot-id`), `rewrite_data`, `rewrite_deletes` (`RewriteFiles`) | снапшот, следующий за базовым | `ValidationException` «Cannot determine history between starting snapshot … and the last known ancestor …» → `base_expired` | D > R, если за D в таблице было больше 20 коммитов (`retain_last`); гарантированно при D > R + I | `MergingSnapshotProducer.java:967-994` (сообщение `:990-994`); проверки `SparkPositionDeltaWrite.java:255-284`, `SparkWrite.java:505,527` |
| `append`, `stream_upsert`, `overwrite` и `insert_overwrite` без опций | — | история не проверяется | не теряется | `AppendFiles` и `ReplacePartitions` без `validate-from-snapshot-id` |

- **Второй путь раньше давал бы ложный К2.** До пересмотра в runner этот `ValidationException` классифицировался бы как `data_conflict`. Теперь `src/runner/ops/errors.py: expire_cause` распознаёт оба сообщения, и `classify` возвращает `base_expired` раньше проверки класса исключения. Тесты — `tests/unit/test_effects.py`.
- **Если удалён только сам базовый снапшот,** CoW и rewrite проходят. История проверяется от следующего снапшота (этап 1: `append_expire` → К1).
- **Прежняя оценка «R/2 + R» была неверной.** Работа теряется при D > R, если базовый снапшот стареет за время операции (для RowDelta — с учётом возраста базы при старте). I сдвигает только момент удаления, от 0 до I после достижения возраста R.
- **Длинные чтения.** Операция, которая читает файлы снапшота, удалённые expire, получит NotFound от хранилища. Классификатор вернёт `unknown`, а не К2: это не конфликт. При R = 600 с и D_max ≈ 243 с таких чтений по априорной модели нет. На этапе 3 доля `unknown` проверяется вместе с `base_expired`.
- При R = 600 с и I = 60 с по априорной модели нет операций с D > R, поэтому `base_expired` от фонового expire не ожидается. Исключение — S6, где expire управляемый.

### История таблицы

- Наибольшая история: S1 — 2,2/с × 660 с ≈ 1452 снапшота (≈1,52 МБ метаданных), плюс единицы от управляемых операций. В режиме `high` компакция идёт раз в 60 с: +11 за 660 с, итого ≈ 1463.
- S0, S2, S3, S5 (поток раз в 10 с): ~66 снапшотов; S4 (раз в 15 с): ~44.
- S6 — ~0,125/с × 1500 с ≈ 190.

`concurrency_levels.*.stream_rate_mult` меняет интенсивность событий, но не период коммитов потоков (`_base.yaml`, S2-R3-06).

### Проверка NFR-1

Бенчмарк этапа 2 (`make proxy-verify`, по умолчанию `BENCH_EXPIRE=true`, `BENCH_SNAPSHOT_BYTES=960`) воспроизводит «пилу» истории S1 между rate·R и rate·(R + I). NFR-1 проверяется на верхней полосе: окна с медианой снапшотов ≥ 0,9 · rate·(R + I), объединённые; верхняя граница ДИ ≤ 5 мс.

### Что переносится на этап 3

На этапе 3 — [auto]-проверки (`tz/06_implementation_plan.md`):
1. Нет операций дольше R (по измеренным D), и `base_expired` / `unknown` от фонового expire не возникают.
2. Наибольшее число снапшотов и байт метаданных в прогонах (runner пишет `table_health`) ≤ B.

При нарушении R пересчитывается по правилу выше. Если общего R нет, решение принимает автор.

Реализация в runner — тоже этап 3: поле `maintenance.expire_snapshots` загрузчика сценариев, слот пула `maintenance`.
