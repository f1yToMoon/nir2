## 1. Цель этапа

Прозрачный прокси REST-каталога с журналированием попыток коммита и восстановлением следов коммитов (tz/06, этап 2; FR-PROXY-1…9, NFR-1).

## 2. Что сделано

- `src/capl/proxy/app.py` (шаги 2.1, 2.6, 2.7): catch-all прокси на Starlette.
  - Цель запроса берётся из `raw_path`/`query_string` без перекодирования.
  - Тело коммита читается целиком (нужно для разбора и удержания), остальные тела запросов передаются потоком.
  - **Ответы передаются потоком сырыми байтами** (`aiter_raw`, без декодирования `Content-Encoding`), в том числе 2xx на коммит. Буферизуются только ответы ≥ 400 на коммит: из них нужен `error_type`. Заголовки ответа — ровно полученные, без hop-by-hop; прокси ничего не добавляет (`Content-Length` к 204 не дописывается, chunked остаётся chunked).
  - Hop-by-hop заголовки удаляются, включая перечисленные в `Connection`. Заголовки `httpx` по умолчанию и `server`/`date` от uvicorn не добавляются.
  - Собственные ответы прокси — только 502 (каталог недоступен) и 504 (таймаут).
  - Сверка целостности `IntegrityProbe`/`IntegrityTransport`: цель запроса, SHA-256 тела и мультимножество заголовков на входе прокси против того, что передано транспорту httpx, на выборке `proxy.integrity_sample_rate`.
  - Режимы `full | passthrough`. Fail-open: вызов advisor в `asyncio.wait_for(…, 20 мс)`, любое исключение → пересылка без удержания. Ошибки собственного учёта (разбор, журнал, обогащение) на ответ не влияют.
  - Задание обогащения ставится в очередь **после того, как клиенту передан последний байт ответа** (и при обрыве соединения клиентом).
- `src/capl/proxy/commit_parser.py` (2.2):
  - pydantic-модели `CommitTableRequest`/`CommitTransactionRequest`;
  - разбор пути (prefix необязателен, `%1F` в namespace);
  - `classify()` по классу коммита Iceberg 1.12.0. MoR: `mor_delete` (только delete-файлы) и `mor_update` (data- и delete-файлы; за ним стоят UPDATE и MERGE с одинаковыми исходами во всех правилах матрицы — `EQUIVALENT`); `replace` без изменения файлов — `rewrite_manifests`;
  - **неоднозначность класса по телу**: `AMBIGUOUS` — 5 случаев с множествами кандидатов, `ParsedCommit.ambiguity`/`candidates` (ADR-007 п. 5, `tz/04` §1.2). Критерий — разный исход кандидатов хотя бы в одной паре правил матрицы;
  - тип ошибки из тела ответа.
- **Класс операции по привязке слот → (`op_id`, `op_type`)** (FR-PROXY-4): `PUT /v1/debug/slots/{slot}`. В журнал пишутся `op_class` (по привязке, иначе по телу), `op_class_body`, `op_class_ambiguity`, `op_class_source` (`op_id` | `body`); DDL — идемпотентные `ALTER … ADD COLUMN IF NOT EXISTS` при старте. Новые классы в `config/conflict_matrix.yaml: op_classes`: `metadata_delete`, `insert_overwrite`, `insert_overwrite_opts`.
- `src/capl/proxy/hold.py` (2.6): ворота удержания с жёстким дедлайном `min(max_ms, hold.max_ms)`. Освобождение — явное, по успешному коммиту указанного слота конкурента, по дедлайну (ворота снимаются), `release_all` при остановке прогона.
- `src/capl/telemetry.py` (2.3): asyncpg, батчи, таблицы `commit_attempts`, `commit_events`, `commit_partitions`, `client_reports`. Неблокирующая очередь, потери считаются метрикой.
- `src/capl/metrics.py` (2.3): метрики Prometheus с именами из дашборда Grafana; плюс `capl_proxy_phase_seconds{phase=body_receive|parse|hold_decision|response_stream}`, `capl_fail_open_total`, `capl_body_integrity_total`, `capl_enrich_*`, `capl_telemetry_*`.
- `src/capl/enricher.py` (2.4): читает manifest list нового снапшота и манифесты с `added_snapshot_id` = снапшот. Берёт записи ADDED/DELETED (с наследованием `snapshot_id` в v2), агрегирует по партициям: добавленные и удалённые data-файлы, добавленные и **удалённые delete-файлы** (`removed_delete_files`), байты; для DML/компакции сохраняет пути удалённых файлов. Пишет `commit_events`, `commit_partitions` и событие в `state`.
  - **Декодирование — в пуле процессов** (`enricher.executor: process`, spawn), чтобы декодирование Avro не держало GIL процесса прокси.
  - Отладка: `PUT /_capl/debug/enricher?on=…&read=…` (без чтения манифестов — для локализации накладных расходов).
- `src/capl/state.py` (2.5): кольцевые буферы по таблицам; интенсивности по окнам 60/300/900 с; детектор периодических писателей; привязка слот → (`op_id`, `op_type`).
- `src/capl/advisor/app.py`: заглушка advisor этапа 2 — удержания, флаг отказа, режим, слоты, `GET /v1/state`, `POST /v1/debug/flush`.
- `scripts/capture_commit_fixtures.py`, `tests/fixtures/commits/` (**29 файлов**, у всех `git_sha` = `ad281f9`, снято `make fixtures-capture` на чистом дереве). Реальные тела коммитов Spark 4.0, Java API и Flink, включая **MERGE только со вставками в CoW и MoR** (`operation=append`), **MoR MERGE только с удалениями** в v2 и v3 (`operation=delete`) и `rewrite_manifests`. Ожидаемый класс фикстуры — выполненная операция (истинный класс). Фикстура задаёт ещё и ожидаемую неоднозначность и проверяет, что истинный класс входит в кандидаты.
- Скрипты экспериментов: `scripts/overhead_enricher_ablation.py`, `scripts/overhead_localization_blocks.py`, `scripts/overhead_localization_timestamps.py`, `scripts/grafana_check.py`.
- Тесты: unit — 118 (`make test-unit`); integration — `tests/integration/test_proxy_stage2.py` (`make proxy-verify NAME=…`). `make lint` проверяет также скрипты этапа 2 и `scripts/update_matrix.py`.

### 4.2 Накладные расходы: от чего растут (S2-R1-02)

По ревью r1 накладные расходы росли с размером таблицы. Механизм разобран по шагам; все артефакты — `results/stage-2/r3/` и `r2/`.

1. **Store-and-forward ответа** (гипотеза ревьюера). Ответ на коммит теперь передаётся потоком. Фазовая метрика `response_stream` введена. Время до последнего байта ответа 540 КБ (gzip; 2,1 МБ после распаковки), 40 чередующихся запросов: через прокси +1,6 мс, хвост передачи одинаков (46,7 и 46,8 мс). Прокси не распаковывает gzip: SHA-256 ответа через прокси и напрямую совпадают. Разбиение на HTTP-чанки тоже одинаково: 154 чанка по ≤ 4096 байт.
2. **Обогащение.** Абляции: блоки по 120–150 коммитов на путь, обогащение включается и выключается через блок; статистика — парная медиана proxy − bypass.

   | Эксперимент (код) | Снапшотов | on | off | noread |
   | --- | --- | --- | --- | --- |
   | пул потоков (`715616c-dirty` — снято на незакоммиченном коде, `r2/enricher_ablation_baseline.json`) | 2200–2950 | 3,63 / 4,24 / 6,09 | 1,94 / 0,74 / −0,29 | — |
   | пул процессов (`85c47e4`, `r2/enricher_ablation_process.json`) | 3100–3850 | 5,53 / 5,59 / 5,70 | 2,10 / −2,48 / 2,16 | — |
   | + очередь после ответа (`18d311a`, `r3/enricher_ablation.json`) | 3577–4327 | 5,70 / 2,17 / 4,59 | 2,88 / 2,07 / 1,91 | — |
   | без чтения манифестов (`45bb0a5`, `r3/enricher_localization_noread.json`) | 5047–5647 | 12,30 / 18,70 | −2,26 / 5,30 | 4,97 / 1,94 |
   | capl на отдельных физических ядрах (`r3/enricher_localization_pinned.json`) | 5767–6127 | 11,32 / 13,34 | −4,06 / −0,46 | — |

   - Пары блоков считаются так: блок on и следующий за ним блок off (`noread` не в счёт) — 13 пар в пяти экспериментах. По парной медиане on > off во всех 13; по разности медиан блоков — в 12 из 13 (исключение — второй блок `85c47e4`: 5,84 против 15,79). Разница создаётся чтением манифестов: при `noread` задание проходит пул процессов и учёт, и это почти бесплатно.
   - Одно чтение при 5647 снапшотах: manifest list 235 КБ, 5647 записей, ~60 мс по времени и ~30 мс CPU в процессе пула.
   - Эксперименты запускались через `docker compose … exec -T -e GIT_SHA=…` с явно переданным коммитом, без автоматического признака `-dirty`. Коммит в таблице — код образа capl на момент эксперимента.
   - Закрепление capl на CPU 8–11, а остальных контейнеров на CPU 0–7 (`docker update --cpuset-cpus`) разницу не убрало.
3. **Где именно задержка** (`r3/enricher_localization_timestamps.json`). Время клиента сопоставлено с отметками журнала прокси. При on и off одинаковы:
   - до входа в обработчик прокси — 1,44 мс;
   - внутри прокси до пересылки — 0,19 мс;
   - время каталога до заголовков ответа.

   Вся разница — в отрезке после заголовков ответа, то есть в передаче ответа и его разборе клиентом (~150–170 мс на 6000+ снапшотах). Фазы, которые измеряет сам прокси, от обогащения не зависят (`r3/enricher_localization.json`: `capl_commit_upstream_seconds` и `response_stream` равны в on и off). Точный механизм влияния чтения манифестов в соседнем процессе на этот отрезок не установлен. Не исключена гипотеза ревью r2. При on результат обогащения приходит через ~60 мс, когда прокси передаёт ответ на следующий коммит, и обработка результата в цикле событий задерживает хвост этой передачи. `response_stream` заканчивается при передаче последнего чанка в `send()` и сброс буфера транспорта uvicorn не охватывает.
4. **Почему рос manifest list.** PyIceberg 0.12.0 по умолчанию не сливает манифесты (`pyiceberg/table/__init__.py:208`, `MANIFEST_MERGE_ENABLED_DEFAULT = False`), и manifest list таблицы бенчмарка рос на запись с каждым снапшотом. Писатели стенда (Spark, Flink — Iceberg Java) сливают манифесты по умолчанию (`TableProperties.java:119,122`: `commit.manifest-merge.enabled=true`, `min-count-to-merge=100`). С `a5f491d` таблицы бенчмарка создаются с этим свойством (в r4 в конце 80 записей против 3000+ в r3). Без слияния: `STAGE2_BENCH_MANIFEST_MERGE=false`.
5. **Итог.** Граница определяется по первому окну, превысившему 5 мс, а не по линейной регрессии. Ряд нелинеен: после ~2100 снапшотов ступенька, а окна 2701 и 2801 занижают наклон.

   | Прогон | Первое окно из 100 коммитов > 5 мс | Окна из 300 коммитов, конец серии | Линейная регрессия (справочно) |
   | --- | --- | --- | --- |
   | r3 (без слияния) | 2201–2300 (7,56 мс) | — | 1,42 мс / 1000, r = 0,68 |
   | r4 (со слиянием) | 2201–2300 (5,23 мс) | 4,95 (2101–2400), 4,05 (2401–2700), 5,65 (2701–3000) | 1,28 мс / 1000, r = 0,72 |

   **Граница выполнения NFR-1 по p50 в этом бенчмарке — ~2200 снапшотов.** Слияние манифестов уменьшило наклон, но первое превышение не сдвинуло. У роста есть и другая составляющая, растущая с размером ответа (метаданные таблицы). Отделить её от шума окон (±4 мс между блоками одного режима) не удалось: ни один прогон при слиянии манифестов не разделяет влияние обогащения и размера ответа.
6. **Граница на снапшотах размера Spark/Flink (S2-R3-02, `r8-boundary`).** У PyIceberg запись снапшота ~544 Б, метаданные растут на ~640 Б на снапшот; у Spark/Flink запись 871–960 Б. Бенчмарк дополняет summary ключами `spark_append_v2` и заполнителем до 960 Б (факт — 970 Б); метаданные растут на 1037 Б на снапшот (13,8 КБ + 1037 Б·n). Без expire, 3000 коммитов на путь. Критерий тот же, что в [auto]-проверке: окна с медианой снапшотов в [T − 300, T], объединённые (300 пар), верхняя граница бутстрепного ДИ ≤ 5 мс.

   | T, снапшотов | Метаданные, МБ | Медиана, мс | 95 % ДИ, мс |
   | --- | --- | --- | --- |
   | 1500 | 1,57 | 3,17 | 2,35…4,19 |
   | 1600 | 1,67 | 3,68 | 2,84…4,88 |
   | 1800 | 1,88 | 3,83 | 2,90…4,97 |
   | 1900 | 1,98 | 4,15 | 2,90…5,17 |
   | 2000–2300 | 2,09–2,40 | 3,0–3,7 | верх 3,63…4,98 |
   | 2400 | 2,50 | 4,48 | 3,31…5,52 |
   | 3000 | 3,12 | 6,70 | 4,32…8,81 |

   Граница принимается консервативно по первому превышению: **B = 1800 снапшотов размера Spark ≈ 1,88 МБ метаданных**. В снапшотах PyIceberg раунда 3 первое превышение было около 2200 (~1,4 МБ при 640 Б/снапшот). Граница не совпадает ни в снапшотах (2200 против 1800), ни в байтах (1,4 против 1,88 МБ); при шуме окон ±2 мс выбрать единицу, в которой граница переносится между клиентами, нельзя. Поэтому для сценариев используется граница, измеренная на снапшотах их размера. Первое окно из 100 коммитов с медианой > 5 мс — 1802 снапшота (6,32 мс, ДИ 2,75…9,90). Bypass p50 — от 13 до 182 мс.

## 6. Проблемы и открытые вопросы

- **NFR-1 на больших таблицах. Решение автора: (б) + (а)** (2026-11-01, `docs/author-decisions.md`). В сценарии добавлен периодический `expire_snapshots` — **модельное допущение** нагрузки, а не практика эксплуатации (S2-R3-05): умолчание Iceberg — 5 суток (`TableProperties.java:421`), свойство таблиц сценариев — 1 сутки. Порог не менялся.
  - **Граница** на снапшотах размера Spark/Flink: B = 1800 снапшотов ≈ 1,88 МБ метаданных (`r8-boundary`, §4.2 п. 6). На таблицах с большей историей NFR-1 по медиане не подтверждён: при 3000 снапшотах — 6,70 мс (ДИ 4,32…8,81).
  - **Ожидаемая история S1 без expire.** Частоту коммитов задаёт `commit_period_s`: Flink — раз в 5 с, 6 агентов — раз в 3 с, итого 2,2 коммита/с, к концу измеряемой части ~3700 снапшотов. `stream_rate_mult` меняет интенсивность событий, а не период коммитов (определение — `_base.yaml: concurrency_levels`, `tz/05`; S2-R3-06).
  - **Выбор R и interval (ADR-008).** Короткий R — меньше история и задержка; длинный R — меньше потерь работы от expire. Нижняя граница по длительностям: R ≥ 2·D_max + hold = 2·243 + 60 = 546 с (D_max — S5 `compliance_delete` по априорной модели `duration_fallback`). Верхняя по NFR-1: 2,2·(R + I) ≤ B → R ≤ 818 − I. При прежнем I = 300 с допустимо R ≤ 518 < 546 — противоречие; I на потери не влияет, поэтому I = 60 с, допустимо R ≤ 758 с. Выбрано **R = 600 с — предварительно**: длительности операций измеряются на этапе 3, там R перепроверяется. Противоречие станет неустранимым, если измеренная D_max > 349 с; тогда решение автора (варианты в ADR-008).
  - **Последствия expire для меток** (S2-R3-03). RowDelta теряет базовый снапшот → `IllegalArgumentException` (`BaseRowDelta.java:134-139`); CoW, overwrite с `validate-from-snapshot-id`, компакция и RowDelta теряют следующий за базовым → `ValidationException` «Cannot determine history …» (`MergingSnapshotProducer.java:967-994`), что раньше дало бы ложный К2. Runner теперь размечает оба пути как `base_expired` (`src/runner/ops/errors.py: expire_cause`, тесты `tests/unit/test_effects.py`). Потеря возможна при D > R, гарантирована при D > R + I.
  - **Режим сценариев (`r9`, `ae712f3`):** история S1 1320–1452 снапшота (≈1,5 МБ), верхняя полоса — медиана 3,58 мс, ДИ 2,47…4,30; разность p95 6,97 мс. Фактическое число снапшотов и байты метаданных в прогонах сценариев проверяются на этапе 3 (`table_health`) против B.
- Механизм роста добавки не установлен; проверенные и отвергнутые гипотезы — §4.3.
- Бенчмарк NFR-1 выполнен клиентом PyIceberg, а не Spark (P4): время отдельного HTTP-запроса коммита в Spark без изменения Iceberg не измерить. Для коммитов Spark есть внутренние метрики прокси.
- Пропускная способность 200 коммитов/с к заглушке (tz/08 §7) — к этапу 8.
- Английский подзаголовок README не приведён к новому названию — решение автора.

## 7. Что переносится в текст ВКР

В данной работе прокси REST-каталога реализован как прозрачный посредник на уровне HTTP-сообщения. Цель и тело запроса, а также поля заголовков, кроме hop-by-hop, передаются без изменений.

Это проверено тремя способами:
- сравнением на записывающем mock-каталоге — цель, тело и заголовки побайтно;
- выборочной сверкой в работающем прокси: 5375 запросов, сравнивались цель, SHA-256 тела и заголовки на входе прокси и на входе HTTP-транспорта; сверка обнаруживает изменения внутри прокси и его HTTP-клиента;
- сравнением ответов с полученными напрямую — 8 типов запросов, включая коды 404, 409 и 500, и успешные коммиты 200 и 204 с полным набором заголовков.

Прокси зафиксировал 1028 из 1028 снапшотов. Восстановленные по манифестам следы коммитов совпали с независимым чтением метаданных на 178 снапшотах (571 пара «снапшот × партиция»). Для добавленных и удалённых delete-файлов следы проверены на таблицах MoR v2 и v3.

Накладные расходы на запрос коммита растут с числом снапшотов таблицы, поэтому они приводятся по окнам из 100 коммитов, а не одним числом. Парная медиана разности «через прокси − напрямую» (снапшоты PyIceberg, ~640 Б метаданных на снапшот, без ограничения истории):
- 1,3–1,6 мс на таблицах до 700 снапшотов;
- 1,9–3,2 мс при 800–2200 снапшотах;
- 5,2 мс в окне 2200–2300 снапшотов — первое превышение порога 5 мс;
- 6,5–7,5 мс в конце серии из 3000 коммитов.

В этой серии без ограничения истории разность 95-х процентилей по окнам из 300 коммитов не превышала 7,3 мс. Обработка запроса в прокси до пересылки каталогу занимает 0,2 мс; ретрансляция ответа в это число не входит, а основная часть накладных расходов приходится на отрезок после получения ответа каталога. Время ответа самого каталога с ростом истории увеличивается сильнее: медиана от 11 до 141 мс за 3000 снапшотов. Механизм роста добавки с размером таблицы не установлен. На таблицах со снапшотами размера Spark/Flink требование к медиане подтверждено до 1800 снапшотов (≈1,88 МБ метаданных): верхняя граница 95 % доверительного интервала парной медианы по объединённым окнам у этой границы — 4,97 мс. Поэтому в сценариях история таблиц ограничивается периодическим `expire_snapshots` (модельное допущение: раз в 60 с, срок хранения 600 с, выбранный по длительности самой долгой операции; срок предварительный и перепроверяется по измеренным длительностям). В этом режиме история не превышает 1452 снапшотов (≈1,5 МБ), и парная медиана добавки по верхней полосе истории составила 3,58 мс (95 % ДИ 2,47…4,30 мс, 1700 пар); разность 95-х процентилей — 6,97 мс.

При отказе компонента advisor прокси переходит в режим fail-open: 438 коммитов из 438 прошли без удержаний.
