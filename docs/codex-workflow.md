Это ограничение проектного хука, а не отсутствие разрешения автора. Обход другим инструментом, отключение хука или изменение доверия агентом не использовались.

Основные хуки уже используются автоматически. В установленном протоколе app-server среди методов hook/trust найден только `hooks/list`; API записи доверия не обнаружен (`results/codex-workflow/native-trust-capabilities.json`). Документированный интерфейс регистрации доверия — `/hooks`. Диалоговое согласие не снимает технический запрет проектного PreToolUse на установку роли; повторное разрешение не требуется, требуется штатное действие, описанное ниже.

## Формат и границы Codex

Официальные источники, открытые при подготовке: [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Skills](https://learn.chatgpt.com/codex/build-skills), [Hooks](https://learn.chatgpt.com/docs/hooks).

Нативная роль задаётся отдельным TOML в `.codex/agents/` с `name`, `description`, `developer_instructions`. Проектные навыки обнаруживаются в `.agents/skills/<name>/SKILL.md`. Роль наследует доступные разрешения, провайдера и MCP родителя: список инструментов Claude и модель Opus не переносятся буквально. Запрет ревьюеру менять реализацию сохранён в инструкции роли; это правило рабочего процесса, а не отдельная изоляция файловой системы. Общие хуки по-прежнему защищают существующие ревью и решения автора. Нельзя утверждать, что нативная роль физически имеет запись только в один новый файл, если это не ограничено внешним sandbox.

Независимость приёмки требует нового контекста без истории реализации, зафиксированного коммита и запрета исполнителю менять артефакты во время ревью. При ограничениях API текущей сессии используется новый CLI/app-server с доступом к установленной роли. Самопроверка и smoke роли не заменяют ревью этапа. Предел — 3 раунда за один запуск stage; переназначение роли его не сбрасывает.

Чтобы завершить установку без обхода хука агентом, автор должен проверить патч и применить его вручную из отдельного обычного терминала:

```bash
cd /home/an/nir
git apply --check docs/codex-workflow-migration.patch
git apply docs/codex-workflow-migration.patch
```

Это действие изменяет только четыре перечисленных файла, не `.claude` и не решения автора. Дополнение защиты новых путей и исправление регистратора runtime-событий подготовлены отдельным [codex-guards-migration.patch](codex-guards-migration.patch); его также проверяет и применяет автор:

```bash
git apply --check docs/codex-guards-migration.patch
git apply docs/codex-guards-migration.patch
git add .codex/agents/stage-reviewer.toml .agents/skills scripts/hooks/guard_pretool.py scripts/hooks/codex_pretool.py scripts/hooks/verify_codex_runtime.py tests/unit/test_codex_hooks.py
git commit -m "codex: install CAPL workflow roles, skills and guard fixes"
```

Перед коммитом автор проверяет `git diff --cached`, не добавляя `.claude/settings.local.json`, `.env` или посторонние файлы. Зафиксировать изменения защищённых файлов должен автор вручную: текущий guard блокирует агентский коммит при наличии таких изменений, даже если они внесены автором. Не менять trust-store и не использовать bypass-флаги.

После изменения адаптеров прежний временный fixture `/tmp/capl-codex-hooks-bjm55x1t` устаревает. До исправления регистратора не следует доверять этому fixture и считать его доказательством нового кода. Создать новый fixture после обоих патчей:

```bash
python3 scripts/hooks/verify_codex_runtime.py --prepare
```

Открыть выведенный временный путь командой `codex --enable hooks -C <путь>`, подтвердить доверие этому проекту и его двум проектным хукам через `/hooks`, затем выполнить `python3 scripts/hooks/verify_codex_runtime.py --run <путь>` либо сообщить путь агенту для запуска. Основные проектные хуки также проверить через `/hooks`: изменение скрипта может потребовать нового доверия. Нельзя объявлять все шесть случаев пройденными до результатов нового runtime-прогона. Все 10 категорий локальных запретов проверены для обоих адаптеров в предложенном патче, но в текущую рабочую защиту этот патч ещё не установлен.

После установки перезапустить/возобновить Codex, проверить обнаружение навыков через `/skills` и выполнить настоящий smoke: поручить Codex запустить **одного `stage-reviewer` без наследования истории**, передать полный `git rev-parse HEAD` и попросить без записи файлов вернуть SHA, роль и два ограничения (только новый файл ревью, без правки реализации). Сохранить транскрипт запуска, ID родителя/ребёнка, выбор роли и ответ; проверить отсутствие изменения дерева. Запуск обычного субагента с похожим текстом не считается проверкой нативной конфигурации.

Для первого формального ревью после всех проверок этапа передать SHA, N=3, K=1, Base=stage-2, отчёт и пути исходных измерений. Проверить заголовок нового файла и состязательный проход, затем закоммитить только ревью. При CHANGES_REQUESTED исправлять до следующего независимого раунда; при PASS* выполнить штатную проверку тега, push, сверку SHA и остановиться перед этапом 4.
