# Инструкции для нейросетевого ассистента (Claude, Codex и др.)

Этот файл — контекст для ИИ-ассистента, который реализует проект по ТЗ. Читать полностью перед началом работы.

## Что это за проект

Магистерская работа (СПбГУ, направление «Большие данные и распределённая цифровая платформа»): **прогнозирование конфликтов оптимистичного контроля параллелизма и конфликт-осведомлённое планирование операций в Data Lakehouse** на примере Apache Iceberg. Реализуемая система — **CAPL** (Conflict-Aware Planning Layer): прокси перед REST-каталогом Iceberg + advisor-сервис + модели риска + исполнитель нагрузки + симулятор.

## Порядок чтения

0. `docs/REVIEWER.md` — правила приёмки этапов (читать до начала любой работы) и открытые ревью `docs/reviews/`.

1. `README.md` — научная постановка (тема, метод, гипотезы).
2. `docs/00_validation_report.md` — почему тема сформулирована именно так (важные технические уточнения).
3. `tz/README.md` → `tz/01_TZ.md` … `tz/08_validation_and_testing.md`.
4. Конфигурации: `config/`, `infra/`, `api/`, `schemas/`.

## Цикл этапа и независимое ревью (обязательно)

Каждый этап выполняется командой `/stage <N>` (скилл `.claude/skills/stage/`) и принимается только по вердикту независимого ревьюера:

1. Реализация по плану этапа и по чек-листу этапа из `docs/REVIEWER.md` §4 (это критерии приёмки).
2. Самопроверка, отчёт `docs/stage-<N>-report.md` с разделом «Ответы на ревью» (по ID каждого замечания), коммит.
3. `/review <N>` — субагент `stage-reviewer` (`.claude/agents/stage-reviewer.md`) в отдельном контексте проверяет артефакты и пишет `docs/reviews/stage-<N>-r<K>.md` с вердиктом `PASS` / `PASS_WITH_NOTES` / `CHANGES_REQUESTED`.
4. `CHANGES_REQUESTED` → исправить все замечания → новый раунд. Не более 3 раундов за запуск, затем остановиться и сообщить автору.
5. `PASS*` → тег `stage-<N>`, push, остановка. На этапах 1 и 4 вместо тега — отчёт контрольной точки и остановка до решения автора.

Принудительно (хуки в `.claude/settings.json`, `scripts/hooks/`):
- тег `stage-<N>` невозможен без ревью с `PASS*` для текущего HEAD, а для этапов 1 и 4 — без решения автора (GO/CORRECT/PIVOT) в отчёте контрольной точки;
- агенту запрещено отмечать «Решение автора» и изменять существующие файлы ревью;
- при старте сессии печатается состояние этапов и последнего ревью.

Если не согласен с замечанием ревью — не игнорируй и не правь ревью: запиши опровержение с доказательством (`файл:строка`, число) в «Ответы на ревью»; следующий раунд его проверит.

## Как работать

- Двигаться **строго по этапам** `tz/06_implementation_plan.md`. Не начинать этап N+1, пока проверки этапа N не пройдены и не написан `docs/stage-N-report.md` по шаблону `docs/templates/stage_report.md`.
- Порядок: сначала подтвердить, что проблема реальна и измерима (этапы 0–4), затем строить решение (5–7), затем проверять гипотезы H1–H4 (7–8). Не начинать модель и политики P5/P6 раньше контрольной точки G2.
- **Контрольные точки G1 (после этапа 1) и G2 (после этапа 4):** посчитать критерии из плана, написать `docs/gate-GN-report.md` по шаблону `docs/templates/gate_report.md` с рекомендацией (GO / CORRECT / PIVOT) и **остановиться**. Продолжать только после того, как автор заполнит поле «Решение автора» или явно ответит в чате.
- В начале каждого этапа: перечитать соответствующий раздел ТЗ, составить список задач, затем реализовывать.
- В конце этапа: выполнить все проверки [auto], записать результаты (числа, а не «работает») в отчёт этапа, обновить `docs/CHANGELOG.md`.
- Если ТЗ противоречит реальному поведению Iceberg/Spark/Flink (версии, имена свойств, API) — **не подгонять под ТЗ**, а зафиксировать факт, исправить конфигурацию и записать ADR в `docs/decisions/`.
- Места с пометкой `VERIFY` в конфигурациях требуют проверки на этапе 0.

## Жёсткие ограничения (нарушать нельзя)

1. **Прокси никогда не изменяет тело или заголовки запросов к каталогу и не формирует ответы вместо каталога.** Единственное разрешённое вмешательство — задержка форвардинга коммита (hold) не дольше `hold.max_ms`. Это основа гарантии изоляции (H3).
2. **Fail-open:** любая ошибка advisor/модели → прозрачное проксирование.
3. **Никаких изменений в коде Iceberg, Spark, Flink, каталогов.**
4. **Point-in-time корректность признаков:** при обучении — только события до момента решения. Один модуль `capl.features` для online, offline и симулятора.
5. **Один код политик** (`capl.policies`) для advisor и симулятора.
6. **Метки исходов** берутся только из runner (`ValidationException` → `data_conflict`, `CommitFailedException` → `retry_exhausted`), не выводятся из ответов каталога.
7. **Воспроизводимость:** каждый прогон определяется `(scenario, variant, policy, concurrency, seed, versions, git_sha)`; всё случайное — от зерна.
8. **Честность результатов:** не подбирать параметры сценариев под успех P6 после просмотра результатов E3. Параметры сценариев фиксируются до серии E3 (тег `exp-v1`). Отрицательный результат — допустимый результат.

## Стек и стиль кода

- Python 3.11, типизация (mypy --strict для `src/capl`), ruff, pytest; pydantic v2 для конфигураций и API.
- CAPL: FastAPI/Starlette + uvicorn, httpx (async), asyncpg, prometheus-client, PyIceberg/fastavro для манифестов, LightGBM.
- Runner: PySpark (версия из образа Spark), requests, psycopg, confluent-kafka.
- Симулятор: SimPy. Анализ: pandas, scipy, statsmodels, matplotlib.
- Логи — JSON (structlog). Конфигурация — YAML + переменные окружения (`${VAR}` раскрываются загрузчиком).
- Небольшие модули с явными интерфейсами (`Protocol`), без глобального состояния, кроме `capl.state` в event loop.

## Ключевые технические факты (проверены при подготовке ТЗ)

- Iceberg 1.12.0 (октябрь 2026): Spark 3.5/4.0/4.1, Flink 1.20/2.1–2.3, Java 17+.
- Конфликт данных проверяется **на клиенте** Iceberg при повторе коммита после 409; каталог видит только 409 и повторы.
- `AppendFiles` не валидирует данные → append никогда не получает конфликт данных; компакция (`RewriteFiles`) не конфликтует с append и (при `use-starting-sequence-number=true`) с equality deletes. Конфликты данных: компакция × DML (симметрично), DML/overwrite × append при `serializable`, DML × DML.
- Уровни изоляции DML: `write.{delete,update,merge}.isolation-level` (по умолчанию `serializable`).
- Повторы: `commit.retry.num-retries` (4), `min-wait-ms` (100), `max-wait-ms` (60000), `total-timeout-ms` (1800000).
- REST-клиент Iceberg добавляет к запросам заголовки из свойств каталога с префиксом `header.` — используется для тегирования слотов (проверить на этапе 0).
- MinIO Community не поддерживается (образы не публикуются с октября 2025, репозиторий архивирован в апреле 2026) → SeaweedFS.

## Что сдавать по итогам каждого этапа

- Код + тесты в репозитории; зелёные `make lint typecheck test-unit` (и `test-int` при поднятом стенде).
- `docs/stage-N-report.md` по шаблону: что сделано; результаты **всех** проверок этапа с числами и командами, которыми они получены; отклонения от ТЗ и их причины; открытые вопросы; формулировки для ВКР.
- ADR в `docs/decisions/` для каждого изменённого решения; запись в `docs/CHANGELOG.md`.
- Полный перечень того, что и где документируется, — раздел «Документирование результатов» в `tz/06_implementation_plan.md`.
- Формулировки «работает», «всё ок» без чисел в отчётах не допускаются.

## Стиль текстов (отчёты, ВКР)

Научный стиль на русском языке по образцу бакалаврской работы автора: «В данной работе...», «Рассмотрим...», «Таким образом...», формальные определения с обозначениями, обоснование выбора методов через «Во-первых... Во-вторых... В-третьих...», таблицы сравнения подходов, англоязычные термины при первом упоминании в скобках (например, «оптимистичный контроль параллелизма (Optimistic Concurrency Control, OCC)»).
